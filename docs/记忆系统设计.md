# 记忆系统设计 v3

> 代码根目录：`backend/src/codegenx/`；表结构 DDL：`init/memory_schema.sql`、`init/chat_message.sql`。

---

## 1. 模块定位与总览

记忆系统负责**跨会话的持久记忆**：让智能体记住用户的偏好、约束、身份、历史经验，并在后续对话中自动生效。它不管会话内的摘要压缩（那是上下文工程的职责，见 `ai_service/compact/`）。

核心设计理念：**MySQL 是唯一真源，其余存储都是可重建的派生层**。

| 存储 | 角色 | 内容 |
|---|---|---|
| MySQL `agent_memory` | 唯一真源 | 全部记忆条目（hot/warm 同表分层） |
| MySQL 元数据三表 | 调度与对账 | 任务队列、消费水位、对账进度 |
| Qdrant `agent_memory_warm` | 可重建检索索引 | 仅 warm 层的向量，payload 只存指针不存正文 |
| Redis | 可丢弃缓存/缓冲 | hot 缓存、命中计数缓冲、提炼互斥锁 |
| 本地 zip 文件 | 归档介质 | 90 天未命中记忆的导出留档 |

记忆分两层：

- **Hot 层（结构化语义记忆）**：硬约束、用户偏好、身份事实等"必须确定性生效"的内容。每轮对话**全量注入** system prompt，不走召回、不进向量库、不做时间衰减。
- **Warm 层（情景记忆）**：带时间的一次性经历（纠正、任务经验、项目背景等）。数量随对话增长，按需**向量语义召回**，参与时间衰减与归档。

代码位置一览（`ai_service/memory/` 包）：

| 文件 | 职责 |
|---|---|
| `models.py` | 记忆条目结构 MemoryEntry、九种内置类型与权重/半衰期、ULID 生成 |
| `memory_manager.py` | 在线门面 MemoryFacade：每轮组装 hot + warm 注入 |
| `hot_store.py` / `hot_cache.py` | hot 层加载注入（token 预算裁剪）/ Redis 缓存（写时 DEL） |
| `retriever.py` | warm 层混合召回 + 三因子重排 + token 窗口 + 命中登记 |
| `vector_store.py` | Qdrant 读写原语（瘦 payload，point id = MySQL 自增主键） |
| `writer.py` | 写入统一入口：准入校验 + 敏感信息拦截 + 分层落库 |
| `trigger.py` | 提炼触发两级漏斗：每轮信号检测 → 阈值触发 |
| `prompts.py` | 提炼 / 矛盾检测 / hot 压缩三类提示词与输出解析 |
| `lifecycle.py` | 每日整理（warm 去重）与衰减归档（30/90 天） |
| `hot_compact.py` | hot 层压缩：同类记忆 LLM 合并 |
| `sync.py` | 向量同步 Worker + MySQL↔Qdrant 双向对账 + 抽检 |
| `compliance.py` | 合规删除级联（MySQL → Qdrant） |
| `locks.py` | 会话级提炼互斥锁（Redis） |
| `hit_buffer.py` | 命中计数异步刷回（Redis Hash 聚合 → 定时落库） |
| `metrics.py` | 指标与结构化日志门面（正文不进日志） |

离线调度在 `ai_service/schedule/`：`memory.py`（MemoryScheduler 调度器）、`memory_task_store.py`（任务/水位/检查点三表 DAO）。
管理接口在 `ai_service/api/memory_router.py`（`/api/admin/memory/*`）。
配置在 `ai_service/utils/config.py` 的 `MemoryConfig`（search / store / trigger 三节）。

## 2. 整体架构与数据流

### 2.1 四条数据流

**检索流（在线，每轮）**：用户输入 → hot 层全量加载（Redis 缓存优先，miss 回 MySQL）→ warm 层向量+关键词混合召回 → 应用层三因子重排 → token 窗口截断 → 拼接冲突处理规则 → 注入 prompt。入口是 `MemoryFacade.load()`（`memory/memory_manager.py`），由智能体在组装 prompt 时调用（如 `agent/agents/leader_agent.py`）。

**写入流（离线，条件触发）**：每轮对话结束 → 轻量信号检测（正则，不调 LLM）→ 累加会话水位计数 → 达到阈值投 `warm_extract` 任务 → 后台 Worker 按水位增量读消息 → 小模型提炼候选 → 准入校验 → 分层写 MySQL（hot 走 upsert，warm 追加）→ warm 批量向量化写 Qdrant → 推进水位。

**生命周期流（离线，每日）**：`consolidate`（warm 精确重复合并 + hot 压缩）、`decay_archive`（warm 30 天未命中软删 → 90 天归档导出 + Qdrant 物理删除）、`conflict_detect`（hot 层矛盾检测）。

**对账流（离线）**：向量同步每 30 秒增量补写；`sync_check` 每日双向对账（补缺失向量 + 清理幽灵点位）+ 召回质量抽检。

### 2.2 两个位点（容易混淆，刻意分开）

| 位点 | 载体 | 语义 |
|---|---|---|
| 提炼位点 | `memory_watermark.last_seq` | 某会话的消息提炼到哪了（对应 `chat_message.seq`） |
| 同步状态 | `agent_memory.vector_synced_at` | 哪些记忆已写入 Qdrant（NULL 即待同步队列） |

同步正确性由行级字段 `vector_synced_at` 保证——它本身就是待办队列，天然幂等，Worker 崩溃重启自动续跑。`memory_sync_checkpoint` 表只做对账任务的断点续跑与审计，不承担正确性。

## 3. 分层职责与类型体系

### 3.1 Hot 层：结构化语义记忆

**定位**：高频、硬性、不可突破的约束与全局事实，每轮必然全量生效。

| 类型 | 说明 | 示例 |
|---|---|---|
| `hard_constraint` | 项目硬性规范、业务强限制 | "所有金额计算保留 2 位小数" |
| `system_rule` | 系统基准规则 | "回复一律用中文" |
| `user_preference` | 用户明确表达的偏好 | "不要使用 emoji" |
| `identity_fact` | 用户身份与稳定事实 | "用户是后端工程师" |
| `external_resource` | 资源指针 | "项目 A 的需求文档在某路径" |

生命周期特点：**只由"被推翻"失效，不因时间失效**。hot 是全量加载不走召回，`hit_count` 不会随命中增长，按访问时间衰减会把硬约束静默删掉——所以 hot 层没有衰减，只有同槽位取代（`superseded`）、撤销（`revoked`）、合规删除三条出路。

体量控制靠**写入期硬上限**（默认 80 条，`memory.store.hot_max_entries`）：写满后拒绝直接写入并转投压缩任务，而不是运行期静默截断——静默丢弃硬约束是正确性事故。

### 3.2 Warm 层：情景记忆

**定位**：带具体时间和上下文的一次性经历，只追加（append-only），发生过就是发生过。

| 类型 | 说明 | 召回权重 | 半衰期 |
|---|---|---|---|
| `user_correction` | 用户对某次输出的纠正 | 1.0 | 60 天 |
| `task_experience` | 历史任务的解法与结论 | 0.8 | 90 天 |
| `project_background` | 项目阶段性背景 | 0.6 | 30 天 |
| `interaction_habit` | 交互习惯观察 | 0.5 | 30 天 |

warm **不做写入判重**："用户上周抱怨啰嗦"和"这周又抱怨"是两条独立的有效记忆，重复反馈的累积正是后续治理的素材。幂等由任务队列保证，不需要在记忆层面判重。

### 3.3 类型体系与状态机

九种内置类型定义在 `memory/models.py`（`BUILTIN_MEMORY_TYPES`），每种类型固定归属层级、召回权重、衰减半衰期；MySQL 侧有对应的 `memory_type_dict` 字典表（种子数据见 `init/memory_schema.sql`）。新增类型的设计意图是"插一行字典表数据即可"，类型字段存 VARCHAR 不用枚举。

记忆条目状态（`agent_memory.status`）：

| 状态 | 含义 |
|---|---|
| 1 active | 正常生效 |
| 2 superseded | 被同槽位新记忆取代（hot 的主要失效方式） |
| 3 revoked | 撤销（提炼出错 / 用户要求 / 合规软删） |
| 4 archived | 衰减软删（30 天未命中）；归档导出后 Qdrant 物理删除 |

**失效硬约束**：任何 status 从 1 改为 2/3/4 必须走单一入口 `memory_store.mark_inactive()`——同一语句内把 `active_slot` 置 NULL（释放 uk_slot 槽位，否则该槽位永久写不进新记忆），warm 行同时把 `vector_synced_at` 重置为 NULL（让同步 Worker 把新状态推到 Qdrant）。

### 3.4 来源与置信度

`source_type`：1=用户明说，2=模型推断，3=人工录入/系统变换。**模型推断的记忆置信度必须 < 0.70 且不得进 hot 层**——hot 只收用户明说和人工录入。这道门槛在提示词（`memory/prompts.py`）和入库校验（`memory/writer.py`）两处都拦截，不依赖 LLM 自觉。

## 4. 存储设计

### 4.1 MySQL 表（DDL：`init/memory_schema.sql`）

| 表 | 职责 |
|---|---|
| `memory_type_dict` | 类型字典：类型编码、分层、展示名、权重、半衰期、是否内置 |
| `agent_memory` | **记忆主表，唯一真源**。hot/warm 同表，靠 `memory_layer` 区分 |
| `memory_task` | 离线任务队列：状态机 pending→running→done，失败退避（1m/5m/30m）超限置 dead |
| `memory_watermark` | 会话消息消费水位 + 漏斗计数（pending_signals / pending_tokens） |
| `memory_sync_checkpoint` | 对账断点与审计（上次扫描位置、补写/清理统计） |

`agent_memory` 的关键设计点：

- **双 id**：`id`（BIGINT 自增主键）同时作为 Qdrant point id（Qdrant 不接受 ULID）；`memory_id`（26 位 ULID，字典序即时间序）是业务 id，对外引用、溯源、回表都用它。
- **uk_slot 唯一约束**（app_id + user_id + subject + memory_type + slot_key + active_slot）：hot 层同槽位仅一条 active。`active_slot` 在 active 时为 1、失效时为 NULL——MySQL 唯一索引允许多个 NULL 共存，于是历史记录无限保留且 active 槽位始终唯一。
- **payload 溯源三件套**：`session_id`（来源会话）、`source_msg_ids`（来源消息 uid 数组，合规级联删除依赖）、`task_id`（提炼批次反查）；另有 `source_agent` 记录产生记忆的智能体名（多智能体写门控配套）。
- `token_cost` 在写入时算好（粗略估算：字符数 ÷ 4），检索裁剪直接用，不在线计算。


**失效硬约束**：
任何 status 从 1 改为 2/3/4 必须走单一入口 `memory_store.mark_inactive()`——同一语句内把 `active_slot` 置 NULL（释放 uk_slot 槽位，否则该槽位永久写不进新记忆），warm 行同时把 `vector_synced_at` 重置为 NULL（让同步 Worker 把新状态推到 Qdrant）。

**记忆类型可扩展、支持 agent 自我进化**: 
落地方式为 `memory_type_dict` 字典表：

- **不用数据库 enum**。`memory_type` 存 `VARCHAR(32)`，由字典表校验。新增类型 = 插一行数据，无需 DDL 变更
- **权重配置化**。召回权重与裁剪优先级存字典表，可在线调整、可灰度，不需要改代码发版
- **agent 自主扩展的类型**标 `is_builtin=0`，可被治理任务审计和回收
- **衰减半衰期按类型配置**，`half_life_d` 为 NULL 表示不衰减（hot 层一律 NULL）

### 4.2 Qdrant（warm 检索层）

单 collection `agent_memory_warm` 全租户共用，启动时由 `vector_store.ensure_warm_collection()` 幂等建库（向量维度取 `config.json` 的 `embedding.dimensions`）。payload 索引对 `user_id` / `app_id` 建 `is_tenant=true` 的 keyword 索引——多租户场景官方推荐的单 collection + payload 分区方案，租户过滤性能显著优于普通索引。

**payload 瘦身**：只存 memory_id / app_id / user_id / memory_type / status / created_at 六个字段，**正文不进 payload**。召回后按 id 回 MySQL 取 summary/content。理由：payload 参与过滤与加载，长文本推高内存；正文的软删/撤销都在 MySQL 做，payload 存一份等于制造第二个真源；回表本来就要做（需要在 MySQL 侧复核 status）。

point 的 status 只有 active / inactive 两档；失效记忆靠 `vector_synced_at` 置 NULL 触发整体重推（upsert 覆盖 payload）。

Point 结构
```json
{
  "id": 10086,
  "vector": [0.0123, -0.0456, "..."],
  "payload": {
    "memory_id":   "01J8ZK3M9P2Q4R5S6T7V8W9X0Y",
    "app_id":      "app_demo",
    "user_id":     "u_10086",
    "memory_type": "task_experience",
    "status":      "active",
    "created_at":  "2026-09-24T16:20:00Z"
  }
}
```

### 4.3 Redis（缓存与缓冲，绝不做真源）

| Key 模式 | 内容 | 失效策略 |
|---|---|---|
| `mem:hot:{app_id}:{user_id}` | 该用户全部 active hot 记忆的最小注入视图（已排序），TTL 24h | **写时 DEL**（不是 SET）：并发写下 SET 容易写回旧值，DEL 让下次读重建 |
| `mem:hit:{app_id}:{user_id}` | Hash：memory_id → 命中计数 + 时间戳伴生字段，TTL 7d | 定时任务批量刷回 MySQL 后 DEL |
| `mem:extract:lock:{session_id}` | 提炼互斥锁，TTL 300s | 自动过期 + Lua 校验令牌释放 |

hot 缓存读取时会二次校验反序列化数据里的 user_id，防 key 拼接错误导致的越权。

### 4.4 对话数据源（chat_message 表）

记忆提炼直接消费 `chat_message` 表（DDL：`init/chat_message.sql`，DAO：`chat_message/store.py`），不另存一份对话。关键字段：

- `seq`：会话内单调递增序号，是提炼位点的载体。生成方式为 `SELECT MAX(seq)+1 ... FOR UPDATE`（靠 uk_session_seq 防重），会话级串行写入下足够。
- `message_uid`：溯源 id，写入记忆的 `source_msg_ids`。
- `content_tokens`：本条消息内容的 token 估算（字节数 ÷ 4），漏斗的 token 计量口径与此一致。
- 超长消息（超过阈值字节数）内容外置为本地 blob 文件，表内存 `payload_ref` 指针（P1-13）。

提炼读接口 `read_since(session_id, after_seq)`：按 seq 升序返回水位之后的消息。

### 4.5 归档文件

90 天未命中的 warm 记忆按月打包追加写入本地 zip：`.data/{user_id}/{app_id}/memory/archive/agent_memory_{yyyyMM}.zip`（`memory/lifecycle.py`），MySQL 行保留（status=4，`valid_to` 置位标记已导出），Qdrant 点位物理删除。导出内容为完整行 JSON，可审计可回溯。

## 5. 在线检索链路

入口：`MemoryFacade.load(query, user_id=, app_id=, session_id=, read_types=)`（`memory/memory_manager.py`）。返回一段注入文本 = hot 段 + warm 段 + 冲突处理规则。总开关 `memory.search.enabled`。

### 5.1 Hot 路（必然生效，不打分）

`hot_store.format_hot_prompt()`：Redis 缓存优先，miss 查 MySQL（全部 active 且未过 valid_to 的 hot 行）并回填缓存；条目按"类型裁剪优先级 + 更新时间"降序排列；按 `hot_token_budget`（默认 2500 token）做预算裁剪。

**溢出策略**：hot 运行期原则上不触发裁剪（写入期已有 80 条硬上限）；万一超预算，截断低优先级部分的同时打 ERROR 级日志，让运维感知"硬约束正在失效"，并应触发 consolidate 压缩。

### 5.2 Warm 路（按需召回）

`retriever.search_warm()`，双通道并行召回：

1. **向量通道**：query 过 embedding → Qdrant 检索 top-N（默认 24，明显大于最终注入条数），强制租户 filter + status=active + 相似度下限（默认 0.45）。
2. **关键词通道**：从 query 提取标识符（路径/表名/URL 等 embedding 弱项）做 MySQL `summary LIKE` 兜底（默认 10 条）。这条通道不依赖 embedding，向量服务挂了它仍可用。

合并去重后**回表**：按 id 从 MySQL 取正文并复核 status=1（Qdrant payload 更新有异步延迟，向量库的过滤只是"尽力而为"，真源侧必须再过滤一次）。

### 5.3 应用层三因子重排

`final_score = 0.7 × sim_norm + 0.2 × decay + 0.1 × type_weight`（权重在 `memory.search.rerank_*` 配置）：

- `sim_norm`：Qdrant 余弦分（[-1,1]）归一到 [0,1]；关键词命中的给保底分 0.35。
- `decay`：半衰期指数衰减 `0.5 ^ (age_days / half_life)`，年龄按 `COALESCE(last_hit_at, created_at)` 算——被反复命中的记忆保持热度；half_life 按类型取（见 3.2 表）。
- `type_weight`：类型权重（见 3.2 表）。

必须在应用层重排的原因：Qdrant 原生排序只按向量距离，不懂衰减。所以要先召回 top-N、算完综合分再截 top-k；只召回 k 条再重排等于没重排。

### 5.4 Token 窗口与注入格式

warm 按 final_score 降序累加 `token_cost`，超 `warm_token_budget` 即停（warm 是概率召回，少一条不影响正确性）。注入时按话题分组展示（`retriever.format_warm_entries_prompt()`）。

末尾附带冲突消解规则（`memory_manager.MEMORY_USAGE_RULES`），三级优先：**hot > warm > 历史，用户当前指令最高**。跨层不按时间比较——warm 里昨天的情景不能推翻 hot 里三个月前的硬约束。

### 5.5 命中登记与埋点

选中注入的 warm 记忆登记命中：`hit_buffer.record_hits()` 写 Redis Hash（检索链路只做这一次轻量写，避免每次检索都更新 MySQL 热点行），调度器每 5 分钟批量刷回 `hit_count` / `last_hit_at`；Redis 不可用时当场回落 MySQL 直写，不丢命中。

检索命中数经 `monitor_pipeline.on_memory_recall()` 上报监控；每轮的 hot/warm 加载都有独立超时（默认 200ms / 1500ms，`memory.search.*_load_timeout_ms`），超时或异常降级为空注入并打降级指标——**记忆加载失败不得阻塞对话**。

### 5.6 按智能体过滤读取

`read_types` 参数（来自智能体配置 `AgentSpec.memory.read_types`，见 `utils/config.py` 的 `AgentMemoryPolicy`）可限定该智能体注入的 warm 记忆类型；hot 层是核心约束不过滤。

## 6. 离线写入链路

### 6.1 触发：两级漏斗（`memory/trigger.py`）

**第一级 · 轻量信号判断（每轮，不调 LLM）**：每轮结束（TURN_END hook）用正则判断本轮消息是否含记忆信号——偏好表达（"我喜欢/不要/以后都/记住"）、纠正表达（"不对/应该是/你搞错了"）、事实陈述（"我是/我在做/我们项目"）、资源指向（路径/URL/文件名模式）。命中则原子累加 `memory_watermark` 的 `pending_signals`（信号类数）和 `pending_tokens`（本轮文本 token 估算）。

**第二级 · 阈值触发 LLM 提炼**，满足任一即投 `warm_extract` 任务：

| 条件 | 默认值 | 配置 |
|---|---|---|
| pending_signals 达阈值 | 5 | `memory.trigger.signal_threshold` |
| pending_tokens 达阈值 | 3000 | `memory.trigger.token_threshold` |
| 有信号且距上次提炼超时 | 30 分钟 | `memory.trigger.idle_trigger_minutes` |
| 会话结束事件 | — | SESSION_END hook 直接投递 |

为什么不只按轮次：50 条"嗯"和 3 条长文档按轮次衡量完全失真，必须叠加 token 量；而每轮都调 LLM 成本不可接受。漏斗把 LLM 调用压缩到真正有信号的批次上。

投递防重靠 dedup 查询（同会话同类型有 pending/running 任务则跳过）。若投递前进程崩溃，调度器每分钟的**兜底扫描**会找出有积压信号且超时未处理的会话补投（`scan_stale_pending`，`memory.trigger.stale_scan_minutes` 默认 15 分钟）。

注意一个职责划分：水位表的 `last_seq`（消费位点）**只由提炼 Worker 推进**，漏斗只累计信号量——两个写者改同一水位会互相踩。

### 6.2 提炼 Worker（`schedule/memory.py` 的 `_do_warm_extract`）

执行流程：

1. **抢会话锁**（`locks.py`，Redis NX EX 300）：抢不到说明同会话有在途提炼，无过错重排 60 秒后再试（不计失败次数）。Redis 挂了降级放行，由水位检查兜底。
2. **按水位增量读消息**：`read_since(session_id, after_seq=last_seq)`，只消费"以 assistant 收尾的完整轮次"——半截轮次留待下次；单次最多消费 80 条消息（防单任务过大）。
3. **写门控**：任务携带来源智能体名，若该智能体配置了 `memory.write_enabled=False`（纯执行类智能体），跳过提炼直接排干水位——不产生记忆，防污染。
4. **小模型提炼**：渲染对话（压缩 tool 内容，单条截 600 字符）→ 提炼 prompt（`prompts.py`）→ 输出候选 JSON。提炼用独立配置的离线模型（`memory.store.model_name`，空则默认模型），信号量限并发（默认 2），有活跃在线会话时先让位 1 秒，走韧性层（熔断/重试）。
5. **准入校验 + 分层落库**（`writer.py`，见 6.3）。
6. **推进水位**：提取成功才把 `last_seq` 推进到消费位置，同时清零漏斗计数、刷新 `last_extract_at`。失败则水位不动，重试覆盖同一区间（at-least-once）。
7. **审计回填**：任务 payload 记录模型、耗时、消费区间、产出 memory_id 列表——不含对话内容。

### 6.3 写入语义（`memory/writer.py` + `memory/memory_store.py`）

**准入校验**（第一道在提示词，第二道在入库代码）：

- 类型必须在九种内置类型内，否则丢弃；
- 敏感信息正则拦截（凭据赋值、API 密钥、私钥块、身份证号、手机号、银行卡号），命中即拒并打 `memory_write_rejected` 指标；
- 模型推断（source_type=2）强制 confidence ≤ 0.69，且不得进 hot 层；
- 空内容、未知类型一律拒绝，宁缺毋滥。

**hot 写入：uk_slot 确定性 upsert**。同事务内两步：同槽位旧 active 置 superseded（释放槽位、记录 superseded_by）→ 插入新 active。不做语义判重、不同步调 LLM 判矛盾——唯一约束已保证同属性只有一条生效，这是确定性的、零成本的、不会漏的。写入后 DEL hot 缓存。`slot_key` 由提炼 LLM 输出（同类偏好须用同一槽位名，提示词中有约束）。

**warm 写入：append-only**。slot_key 填 memory_id 自身，天然不冲突；`vector_synced_at` 置 NULL 入同步队列。不判重（理由见 3.2）。

**向量跟进**：一批 warm 写入后，批量 embedding + 批量 upsert Qdrant（禁止逐条），成功则标记 `vector_synced_at`。失败不回滚 MySQL——留 NULL 由同步 Worker 和每日对账补写。MySQL 成立即写入成功，向量层允许短暂落后。

### 6.4 任务队列机制（`schedule/memory_task_store.py`）

`memory_task` 表承载全部离线任务，语义 at-least-once：

- **领取**：单事务内 `SELECT ... FOR UPDATE SKIP LOCKED` + UPDATE 置 running，多消费者也不重发（当前单消费者，双保险）。
- **失败退避**：retry_count+1，按 1m/5m/30m 回 pending；超限置 dead 并告警。
- **幂等键** `idempotency_key`：唯一约束，同键只插得进一条。合规删除用 `{app_id}:{user_id}:{request_id}`，每日任务用 `{app_id}:{user_id}:{日期}` 天然防重。
- **心跳**：任务执行中每 30 秒 touch `updated_at`，防长任务被卡死回收误杀。
- **卡死回收**：巡检把 running 且 10 分钟未心跳的任务复位 pending（Worker 崩溃的兜底）。
- **审计**：done 时回填 `produced_count` 和结果 payload（JSON_MERGE_PATCH 合并，不覆盖入参）。

重复执行的兜底：hot 由 uk_slot upsert 天然幂等；warm 可能重复写，由每日 consolidate 的精确去重和 conflict_detect 兜底清理。

## 7. 调度器 MemoryScheduler

`schedule/memory.py`，进程级组件（BaseComponent），随应用生命周期启停：

- **启动**：`recover_running()` 把遗留 running 任务复位 pending（崩溃恢复）→ 预热提炼模型客户端与熔断器 → 启动消费循环。MySQL 暂不可用只降级记忆离线功能，不阻断主服务。
- **停止**：宽限 10 秒等在跑任务 → 超时取消 → running 复位 pending（下次启动续跑）。

主循环是**单消费者**：每轮先做内嵌周期作业，再领取到期任务（默认每批 5 个、空闲轮询 15 秒）逐个执行。内嵌周期作业：

| 作业 | 间隔 | 内容 |
|---|---|---|
| 向量同步 | 30s | 扫 `vector_synced_at IS NULL` 的 warm 行，批量 embedding + upsert + 标记（`sync.run_forward_sync_batch`） |
| 巡检 | 60s | 卡死回收 + 刷新 dead 任务指标 + 漏斗兜底扫描补投 |
| 命中刷回 | 5min | Redis `mem:hit:*` Hash 聚合批量回写 MySQL 后 DEL（`hit_buffer.flush_all`） |
| 每日登记检查 | 60s | 到点（`memory.store.consolidate_hour`，默认凌晨 3 点）后登记当日 consolidate / decay_archive / sync_check / conflict_detect 任务，按"今天是否已登记"判重 |

分发的任务类型：`warm_extract`（提炼）、`consolidate`（整理）、`decay_archive`（衰减归档）、`sync_check`（对账）、`conflict_detect`（矛盾检测）、`compliance_delete`（合规删除）。

LLM 资源管控：独立小模型 + 信号量限并发 + 在线让位，离线提炼不挤占在线对话资源；错误按 LLMErrorClass 分类记入 `last_error`，区分模型故障与本地 bug。

## 8. 生命周期治理

### 8.1 每日整理 consolidate（`memory/lifecycle.py` + `memory/hot_compact.py`）

- **warm 精确重复合并**：同租户同 summary 的 active warm 只留最新一条，其余置 superseded（纯 SQL，不耗 LLM）。
- **hot 压缩**（LLM）：active 条数达硬上限 80% 才触发，按 (subject, memory_type) 分组、组内 ≥2 条交给 LLM 合并为一条（要求逐条保留语义，输出 merge=false 或解析失败就放弃该组，宁缺毋滥）；`hard_constraint` 默认豁免不压；压缩条 source_type=3（系统变换，非推断）；slot_key 取组内最老条，后续同槽写入自然落在压缩条上。单次每租户最多压 10 组，封顶成本。

### 8.2 衰减与归档 decay_archive（`memory/lifecycle.py`）

只作用 warm 层（hot 豁免，原因见 3.1）：

1. **软删**：`COALESCE(last_hit_at, created_at)` 距今超 30 天（`memory.store.decay_days`）→ status=4。分批 LIMIT 执行避免长持锁；数据仍在可恢复。
2. **归档**：软删后再满 60 天（累计 90 天，`memory.store.archive_days`）→ 导出本地 zip（按月打包）→ MySQL 置 valid_to 防重复导出 → Qdrant 物理删除。归档后该记忆不再可语义召回（当前采用彻底归档方案，见 TODO）。

### 8.3 矛盾检测 conflict_detect（`schedule/memory.py`）

每日按租户投递（幂等键带日期防重）：取该用户全量 active hot（体量小），LLM 两两比对找语义冲突（如"回复用中文" vs "英文场景用英文"），命中则保留 created_at 较新的一条，旧的置 superseded，打结构化审计日志。**不阻塞写入链路**——它是异步兜底，不是写入门槛。

## 9. 一致性与对账

**MySQL 是唯一真源**这个定位让一致性大幅简化：不需要分布式事务，派生层（Redis/Qdrant）落后甚至丢失都能从 MySQL 重建。

- **实时同步**：写入路径先 MySQL 后 Qdrant；状态变更（失效/软删/撤销）一律把 `vector_synced_at` 重置为 NULL，由同步链路把新状态推过去。
- **向量同步 Worker**（30 秒一轮）：`vector_synced_at IS NULL` 即待办队列，批量补写；排除 10 分钟内的新行（在途写入由写入链路内联同步，这里只兜底）；积压超 5000 条告警（说明同步链路故障）。Qdrant collection 被清空/损坏时无需手工恢复——全量置 NULL 重跑即从 MySQL 完整重建。
- **每日对账 sync_check**（`memory/sync.py`），双向：
  - 正向：再推一批待同步（兜底当日残留）；
  - 反向：按租户 scroll Qdrant 点位对照 MySQL——Qdrant 有而 MySQL 无或已失效的"幽灵点位"物理删除（少了反向对账，被撤销的记忆会白占 top-k 名额）；
  - 抽检：随机 100 条 active warm 用其 summary 自检索，命中自己为正常；未命中超阈值告警（召回质量问题不报错，只表现为"助手变笨"）；
  - 进度回写 `memory_sync_checkpoint`（断点续跑 + 审计）。
- **并发控制**：多实例写记忆的正确性由 MySQL 事务 + uk_slot 唯一约束保证；同会话并发提炼由 Redis 锁 + 水位推进检查双保险（锁失效时第二个 Worker 推进水位会发现 last_seq 已前进，丢弃结果）；缓存并发靠写时 DEL。

## 10. 多租户与数据隔离

`app_id` + `user_id` 两级隔离：

- **MySQL**：`memory_store.py` 是唯一数据入口，所有查询强制携带 app_id + user_id，索引均以 app_id/user_id 为前缀；业务代码不裸写 SQL。
- **Qdrant**：单 collection + payload 分区（`is_tenant=true`），所有检索强制带租户 filter（`vector_store._tenant_filter`），不存在无 filter 的检索路径。
- **Redis**：key 带 `{app_id}:{user_id}` 命名空间，hot 缓存反序列化后二次校验 user_id。
- **多智能体维度**：记忆按 app+user 全局共享（不按智能体分片），但每个智能体可通过 `AgentSpec.memory` 配置读过滤（read_types）与写门控（write_enabled / write_types），产生的记忆落 `source_agent` 溯源。

## 11. 容灾与降级

记忆系统是**增强组件而非核心链路**——它挂了，对话继续，只是"没记性"。三条硬性原则：记忆加载失败不得阻塞对话；降级必须可观测（统一打 `memory_degrade_total` 指标）；异步链路失败必须能自愈（位点 + 幂等键 + 对账三件套）。

| 故障 | 降级行为 |
|---|---|
| Qdrant / embedding 不可用 | warm 向量通道降级为空，关键词通道仍可用；hot 完全不受影响（不走向量）；待同步队列堆积，恢复后自动追赶 |
| Redis 不可用 | hot 直查 MySQL；命中登记回落 MySQL 直写；提炼锁降级放行（水位检查兜底） |
| MySQL 不可用 | hot 靠 Redis 缓存 TTL 内只读降级；记忆加载/提炼整体降级，对话主链路不受影响 |
| LLM 提炼服务不可用 | 任务退避重试，水位不前进；恢复后自动追赶，幂等键保证不重复 |

## 12. 可观测性

### 12.1 指标（`memory/metrics.py` → `monitor/prometheus_metrics.py`）

- 写入链路：提炼触发计数（按 signal/token/timeout/session_end/stale_scan 分标签）、提炼成功率与延迟、准入拒绝计数（empty/type/sensitive/inferred_hot/hot_full）、dead 任务数、卡死回收计数。
- 同步链路：待同步队列长度、同步失败计数、对账补写/清理/抽检未命中计数。
- 检索链路：hot token 使用率与条数、降级计数（按 qdrant/redis/mysql/embedding/timeout 分标签）、归档计数、矛盾检测命中、压缩合并数。

埋点绝不抛异常、绝不阻断业务。

### 12.2 结构化日志

关键操作（hot 压缩、矛盾解决、合规删除等）打结构化事件日志，只含元数据字段。**summary/content 一律不进日志**（可能含用户隐私），排错用 memory_id 回 MySQL 查——这是硬要求。

### 12.3 管理后台与排查工具（`api/memory_router.py`，`/api/admin/memory/*`，管理员鉴权）

| 接口 | 用途 |
|---|---|
| GET `/list` | 按租户列出记忆全貌 |
| GET `/{memory_id}/trace` | 溯源：source_msg_ids → chat_message 原始消息 |
| GET `/task/{task_id}` | 提炼批次反查：任务行 + 消费区间 + 产出记忆 |
| POST `/retrieval-sim` | 模拟检索：双路原始分 + 逐因子重排明细，不登记命中，还能报告幽灵点位 |
| POST `/rebuild-vectors` | 单用户向量重建：清 Qdrant 点位 + vector_synced_at 全置 NULL，同步 Worker 自动重灌 |
| POST `/deactivate` | 停用记忆（status=3，走 mark_inactive 硬约束） |
| POST `/update` | 编辑记忆（新条取代旧条，source_type=3 人工录入） |

一切修改走接口而不是直接改库——手改 MySQL 不会失效 Redis 缓存、也不会触发向量重同步。

## 附录 A：人工审阅视图

**MySQL 是真源，文件是导出视图。**

```
每日定时任务
  → 按用户渲染 hot 记忆为 markdown + JSON 双格式
  → 写入对象存储：oss://memory-review/{app_id}/{user_id}/{yyyy-mm-dd}.md
  → 保留最近 30 天，供人工查看与 diff
```

**关键约束：这份文件是只读的，不参与在线读写链路。**

人工编辑必须走管理接口写 MySQL，接口负责：
1. 校验 `memory_type` 在 `memory_type_dict` 内且 `enabled=1`
2. 走 `uk_slot` upsert 逻辑（含 `active_slot` 维护）
3. `source_type=3`（人工录入），`confidence=1.00`
4. 失效 Redis 缓存
5. 若为 warm 层，`vector_synced_at` 置 NULL 入同步队列
6. 写审计日志

导出视图完整满足诉求：可看（markdown 渲染）、可 diff（每日快照对比）、可审计（对象存储版本控制）、可回溯（MySQL 里保留全部 superseded 历史记录）。

## 附录 B：Qdrant 换 embedding 模型的重建流程

embedding 模型或向量维度变更时，用 collection alias 做零停机切换（Qdrant 官方推荐做法，alias 变更是原子的，并发请求不受影响）。落到 `vector_rebuild` 任务：

```
① 建 agent_memory_warm_v2（新维度 / 新 metric）
② 建同名 payload index（含 is_tenant）
③ 应用层开启双写：新记忆同时写 v1 和 v2
④ 后台任务：从 MySQL 全量读 active warm 记忆
   → 用新模型批量 embedding
   → 批量灌入 v2（point id 仍用 agent_memory.id，保持不变）
   （这一步是"从 MySQL 读"而不是"从 v1 scroll"——
     有真源时重建是一次简单的 SELECT 全表扫描；
     没有真源时是一次痛苦的全量 API 导出，且要处理分页与并发写入）
⑤ 追平校验：v2 的 point 数 == MySQL 中 layer=2 且 status=1 的记忆数
⑥ 原子切换 alias：
   POST /collections/aliases
   { "actions": [
       { "delete_alias": { "alias_name": "warm_prod" } },
       { "create_alias": { "collection_name": "agent_memory_warm_v2",
                           "alias_name": "warm_prod" } }
   ]}
⑦ 关闭双写，观察 1~3 天
⑧ 删除 v1
```

**注意**：Qdrant 的 collection snapshot **不包含 alias**，alias 需要单独迁移或重建。灾备演练时容易漏掉这一步。另外分布式部署下 snapshot 必须**每个节点单独创建**，单个 snapshot 只含该节点的数据——所以不要把 Qdrant snapshot 当主备份手段，MySQL 的全量备份 + binlog 才是恢复基线。

应用代码全程只访问 alias `warm_prod`，不直接引用 collection 名。
