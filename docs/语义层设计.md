# 语义层设计（数仓元数据理解与检索）

> 版本：v1.0（2026-10-24）  状态：S0 已落地（Pagila 实测通过）

## 1. 背景与目标

数据分析智能体从"单库 MySQL"演进到"数仓多 schema / 跨集市 / 数百张表"后，全量 DDL 注入 prompt 不可行。需要一个语义层回答三件事：

- **有哪些表、表是干什么的**（元数据 + 业务含义）
- **表之间怎么 JOIN**（关系图，含置信度）
- **业务指标怎么算**（指标口径，而非让模型现编）

目标：支撑自然语言提问 → 数据分析的全链路，规模从 15 张表（Pagila）平滑演进到数百张表、多数据源。

## 2. 总体架构与关键决策

### 2.1 决策：内嵌模块 + 工具契约，不是子智能体、不是独立服务

| 方案 | 结论 | 理由 |
|---|---|---|
| 内嵌模块 + 工具 | **采用** | 检索是确定性查表，不应引入额外 LLM 决策；单消费方，同仓库同发布 |
| 新增"数据管家"子智能体 | 不采用（在线链路） | 每次查表多一轮模型调用，延迟和不确定性翻倍 |
| 独立服务 + A2A | 暂缓 | 无第二个消费系统；A2A 是任务委托协议，不适合元数据查询 |
| 离线语义建模 Agent | 预留 | 离线补全描述、人工审核流程，不阻塞在线请求 |

**抽取边界**：语义层只通过 5 个工具对外暴露，契约先行。将来有第二个消费方（BI、其他团队 Agent）时，整体提升为 `codegenx/semantic` 同级模块并暴露 **MCP**（工具/数据服务的标准协议），而不是 A2A。

### 2.2 存储：全部放 PostgreSQL（pgvector），不上图数据库

- 向量检索、关系遍历、结构化过滤在同一实例同一事务完成，避免跨库拼装
- 关系边用关系表 + 递归 CTE 遍历；图数据库（Neo4j/AGE）只有在多跳血缘高频查询、节点规模 10⁵+ 时才评估
- 向量模型维度与 `config.json embedding.dimensions` 绑定（当前 512），**模型选定后不更换**（更换 = 全部重灌）

### 2.3 架构图

```
用户提问
   │
   ▼
leader ──dispatch──► data_explore
                       ├─ search_tables / search_metrics  ┐
                       ├─ describe_table_card             ├─ 语义层检索（在线）
                       ├─ find_join_path                  ┘
                       ├─ find_verified_queries（few-shot）
                       └─ execute_sql → 只读执行 → 报错回填修正
                                        │
                          语义层真源（PostgreSQL semantic schema）
                catalog / 卡片 / 关系 / 指标 / 已验证问答 / 向量
                                        ▲
                      离线采集 + LLM 补描述 + 人工审核（crawler）
```

## 3. 存储设计（init/semantic_schema.sql）

schema=`semantic`，7 张表：

| 表 | 作用 | 关键字段 |
|---|---|---|
| meta_datasource | 数据源注册（跨集市入口） | name, dialect, dsn_secret_ref |
| meta_schema | 库内 schema | domain（主题域路由） |
| meta_table | 表卡，召回主单元 | business_desc, grain, primary_key, row_estimate, tags, status, source_hash, embedding |
| meta_column | 列卡 | business_desc, synonyms, is_pii, cardinality, sample_values, embedding |
| meta_relation | JOIN 关系边（无向遍历） | from/to_columns, rel_type(fk/declared/inferred/mined), confidence, provenance, verified |
| meta_metric | 指标卡（指标即代码） | definition, expression(SQL片段), default_filters, grain, dimensions, version, status |
| meta_verified_query | 已验证问答（few-shot） | question, sql, result_summary, verified_by, embedding |

关键设计：

- **status 状态机**：`draft`（未审核）→ `verified`（可召回）→ `deprecated`。当前 bootstrap 阶段 draft 也参与召回（打标 + 降权 0.05），等人工审核流程上线后收紧为只召回 verified
- **source_hash**：表结构指纹（注释+列定义），驱动增量采集判重
- **关系边必须带来源与置信度**：fk=外键(1.0)、declared=人工声明、inferred=命名推断、mined=查询日志挖掘。模型据此判断 JOIN 可信度，禁止自行猜连接键
- 索引：表卡/指标/问答 HNSW（cosine），名称/描述 gin_trgm_ops（中文按字符 trigram，跨语言主要依赖向量通道）

## 4. 在线检索（semantic/retrieval/hybrid.py）

**检索单元是卡片，不是 DDL**。`CREATE TABLE` 文本的 embedding 质量差（同构表向量趋同），卡片文本才携带业务语义。

- **混合召回**：`score = 0.7 × (1 - cosine距离) + 0.3 × trigram相似度`，verified +0.05，低于 minScore 丢弃
- **两级下钻**：search_tables 先召回 top-8 表卡 → describe_table_card 按需展开列清单（禁止全量列直给）
- **降级策略**：embedding 超时/失败自动退化为纯关键词通道；向量维度异常时退化一次并重试。语义层故障只降级、不阻断分析主链路
- **上下文预算**：build_context 组装（表卡+指标+已验证问答）超过 contextMaxChars 自动截断
- 中文提问对英文表名的场景，关键词通道召回为 0 是预期行为，依赖向量通道

## 5. 离线采集（semantic/catalog/pg_crawler.py）

```
python -m codegenx.ai_service.semantic.catalog.pg_crawler \
  --name pagila --dsn "postgresql://user:pass@host:5432/postgres"
```

- 采集 `pg_catalog`：schema/表(含视图)/列/主键/FK/注释/行数估算
- **bootstrap 启发式**：有表注释 → verified（数仓 COMMENT 通常人工维护）；无注释 → draft。**LLM 生成或推断的描述一律先 draft，不得自动 verified**
- **幂等与人工保护**：重跑不覆盖人工补全的 business_desc，不回退 verified/deprecated 状态；列/表按最新 catalog 增量清理
- 采集器是独立入口的离线任务，不进在线请求链路；也是将来服务化拆分时最自然的第一刀

## 6. 工具契约（tools/semantic.py，label=data_analysis）

| 工具 | 职责 | 关键参数 |
|---|---|---|
| search_tables | 问题 → 候选表卡 | query, datasource?, domain?, top_k |
| describe_table_card | 单表列卡精读 | table, schema?, datasource?, detail |
| find_join_path | 两表 JOIN 路径（带置信度） | from_table, to_table, max_hops |
| search_metrics | 指标口径检索 | query, top_k |
| find_verified_queries | 历史已验证问答 few-shot | question, top_k |

约定：`datasource` 省略时取会话 db_name → store 层兜底唯一数据源；失败提示附带已注册数据源列表。命名避开已有 `describe_table`（MySQL 直查）。

## 7. 配置

- `backend/config.json → semantic`：recallTopK / metricTopK / verifiedQueryTopK / hybridVectorWeight / minScore / maxJoinHops / contextMaxChars / embedTimeoutSeconds
- `backend/config.json → databases`：dbName → 方言与默认 schema（如 `business → postgres/dvdrental`），未登记的库按 MySQL 处理
- `backend/.env`：POSTGRES_HOST/PORT/USER/PASSWORD/DB/POOL_*（元数据库连接）；SEMANTIC_TARGET_DSN（采集目标，CLI 可覆盖）
- data_explore 白名单已加入 5 个工具；`maxToolIterations` 1→6（否则 search→describe→execute 链路一步即断）

## 8. 一步到位决策清单（不定会返工的）

| 决策 | 现在就要做 | 返工代价 |
|---|---|---|
| embedding 模型定版 | 选定后不换（当前 qwen3.7-text-embedding-flash / 512 维） | 全部卡片重灌 + 已审核资产重做 |
| domain 字段采集时填充 | crawler 增加 schema→domain 映射配置 | 数百张表后全量回填 |
| app 绑定升级为 datasource 列表 | 会话路由从单 db_name 演进 | 上线后改会话路由 |
| 业务库凭据独立化 | 按 meta_datasource.dsn_secret_ref 解析 DSN，不假设同实例同账号 | 接第二个集市时执行层返工 |
| crawler 增量同步 | upsert 前比 source_hash，未变跳过 | 数百表全量重写成本与冲突风险 |

## 9. 分阶段升级路径

| 阶段 | 规模 | 做什么 | 明确不做 |
|---|---|---|---|
| S0（当前） | ~30 表（Pagila） | 采集器 + 卡片 + 混合检索 + JOIN 路径 + 工具接入 | 列级召回、rerank |
| S1 | ~100 表 | 增量采集；domain 路由；列级向量召回（search_columns）；补 verified query 库 | 跨库联邦 |
| S2 | 数百表、多 schema | 评估集驱动调参（execution accuracy + recall@k）；二阶段 reranker；查询日志挖掘 JOIN 边（mined）；反馈闭环（用户确认自动入 verified query） | 图数据库 |
| S3 | 跨 datasource | 血缘（优先接 dbt manifest / 上游元数据，不自建血缘引擎）；PII 脱敏；语义层抽服务（MCP）；跨库仅在 leader 层指标组合，不做实时联邦 | — |

## 10. 与工业界主流的对照与差距

架构形态对齐：Snowflake Cortex Analyst（semantic model）、Databricks Genie（space + example SQLs）、Vanna（RAG + verified pairs）、WrenAI（MDL）、Cube/dbt（metrics-as-code）。不上图数据库、MCP 优先于 A2A，也与主流一致。

真实差距在深度而非架构，按优先级：

1. **评测集**：golden set（问题→期望 SQL）+ execution accuracy，一切调参的前提
2. **反馈闭环**：用户确认/纠错自动沉淀为 verified query（主流方案拉开准确率差距的核心）
3. **列值采样**：low-cardinality 列样例值对 WHERE 条件生成影响极大（BIRD 结论），sample_values 字段已建待填
4. **dbt manifest 摄入**：生产数仓的描述/血缘主来源，比人工补注释现实
5. **治理工作流**：审核界面与 steward 角色（当前只有 status 字段）

## 11. 明确不做

- 全量 DDL 塞 prompt；LLM 在 ReAct 循环里自由翻 information_schema
- 纯向量检索（必须混合 + 结构化过滤）
- 让模型自行推断 JOIN 键（必须走已登记边 + 置信度）
- 无外部消费方时拆 A2A 服务；自建血缘引擎；现阶段引入图数据库

## 12. 实测记录

2026-10-24（Pagila @ postgres/public）：

- 本地 PG 16.15 + pgvector 0.8.2 + pg_trgm 1.6，schema 已创建
- Pagila 采集：30 表 / 173 列 / 36 条 FK / 30 张表卡向量化；重跑幂等通过
- 检索实测：`客户租了哪些电影` → film_list / film / rental；`rental→film` 返回 2 跳路径（rental.inventory_id → inventory → film.film_id，置信度 1.0）
- 已知偏差：Pagila 无表注释导致全部 draft，bootstrap 阶段 draft 参与召回（打标 + 降权）

2026-10-25（dvdrental @ business/dvdrental）：

- 业务库迁至 database=business / schema=dvdrental，数据源登记名 `business`
- 重新采集：22 表 / 128 列 / 18 条 FK / 22 张表卡向量化
- 检索实测：`找出还没有归还的租赁记录…` 召回 film_list / customer_list / film_actor / film / customer / rental 等
- execute_sql 已打通 PG：`SELECT ... FROM film` 通过事务级 `search_path=dvdrental` 执行
- 语义层 schema 曾因 `DROP EXTENSION vector CASCADE` 丢失 embedding 列，`init/semantic_schema.sql` 已增加幂等补列语句
