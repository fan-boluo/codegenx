# Agent 三层记忆系统设计方案

采用json 文件 + 向量数据库双数据源的存储方式，分三层设计

# 一、两层记忆分层职责与生命周期设计

## 1\. Warm 主题记忆（中长期持久层）

**职责**：负责存储长期记忆，按主题存储，包括用户固定偏好、用户历史纠正反馈、项目背景信息、资源文件路径、历史任务经验、交互习惯等主题类记忆。

存储到文件和向量数据库

## 2\. Hot 核心记忆（常驻强约束层）

**职责**：负责存储**高频、硬性、不可突破的核心约束与全局规则**，例如项目硬性规范、业务强限制、系统Prompt基准规则。

存储到文件中，体量严格控小，每次组装 Prompt 直接加载。

# 二、双数据源存储架构（json \+ 向量库）

系统采用**双介质存储架构**，各司其职，解决单一存储的缺陷：

1\.**json 文件（真相源）**：作为唯一可信原始数据源，结构化存储每条记忆内容、时间戳、状态、类型，支持人工查看、编辑、审计、回溯，解决向量库不可读、无法排错的问题。

2\. **向量数据库（检索加速层）**：存储记忆向量，提供高效语义召回，解决纯文件检索速度慢、无法语义匹配的问题。

两层数据保持最终一致性，写入以文件为准，检索以向量库为准。

# 三、记忆写入机制设计

## 1\. 写入触发逻辑

hot\warm的写入在每轮对话结束后触发判断是否要进行提取，从对话中获取要提取的原始文本，每10轮触发一次提取。明确记忆写入的要求：识别对话中的**确定性、长效性信息**，仅用户明确的偏好、纠正、项目规则、固定信息允许写入；临时闲聊、不确定猜测、瞬时内容禁止写入。

## 2\. 写入

hot层直接写入json文件

warm层的写入，异步后台执行

先写入文件，后写入数据库

json文件中记录写入时间，记忆文本，记忆id,会话id，记忆主题。

向量数据库中同步写入

写入时会先根据主题做召回判断是否重复，是否语义矛盾（用大模型去做）。重复则不再写入，矛盾则将原来的置失效并新增

每次全部写入完，记录同步的checkpoint到系统元数据，方便定时任务做检查查漏补缺

每个文件最多写入20M，超出则新建文件

# 四、记忆查询与检索机制设计

检索并非直接使用用户原始问句，采用**综合打分 \+ 冲突处理 \+ 窗口截断**的完整链路。

## 1\. 检索召回

hot层直接加载，warm层的加载：向量语义检索，召回TopK候选记忆。

检索：按照关键词+语义混合检索召回，更新片段的最后访问时间。

重排序：打分来源按照以下三种加权0.7 0.2 0.1

语义相似度（主权重）\+ **时间衰减**（新记忆权重更高）\+ 记忆类型权重（用户纠正 \> 普通背景）

语义相似度是算出来的，时间衰减是拿到片段的创建时间算出来的，记忆类型权重是固定的，就是下面几个

- `user_correction` 用户纠正反馈：权重 1.0
- `user_preference` 用户偏好：权重 0.8
- `project_background` 项目背景：权重 0.6
- `resource_path` 资源路径信息：权重 0.5

之后选取topk返回

**记忆类型的扩展**

目前是这几个，后续增加agent的自我进化，将记忆类型做成可扩展的，让agent进行自我扩展

### 2. 上下文窗口控制

hot warm 层的总大小有显示，hot最多xxxtoken, warm层最多xxx。

裁剪的时候：

hot 截断后面的，warm优先高分，最新记忆，严格控制总Token，防止上下文溢出。

## 3\. 记忆冲突解决

虽然在写入的时候有做，但是还是难免会有冲突，比如hot和warm，不同主题的，此时在Prompt中注入冲突处理规则，以最新时间的为准。

# 五、记忆衰减、删除与归档机制

解决记忆无限膨胀、检索变慢、过期内容干扰的问题，采用**软删除 \+ 冷热分层 \+ 时间衰减**体系。

后台定时任务执行。记忆权重时间衰减，30天未访问软删除，90天未访问归档，三种策略解决记忆膨胀问题

## 1\. 记忆自动衰减

- 时间衰减：记忆随创建时间、最后访问时间自动降低权重（四检索部分有写）；

## 2\. 记忆删除策略

30天未访问过期,全部采用**软删除**：json 文件标记失效状态和失效时间，向量库同步更新状态标签，检索时自动过滤失效记忆。不物理删除原始数据，保障可回溯、可审计、可恢复。

## 3\. 归档

文件归档：90天没有更新的文件自动归档压缩

冷热分离：长期未调用、低权重的老旧记忆，从主向量库归档至冷存储：

> 90天未访问 -> 压缩打包存入对象存储（如S3/OSS），并从向量库中**物理删除**。

# 六、双数据源一致性同步方案

解决 json 文件与向量库数据不一致、同步延迟、宕机丢失问题，采用**实时增量同步 \+ 定时兜底校验 \+ 文件变更监听**三重保障。

## 1\. 实时写入同步

记忆新增后，实时同步更新向量库，保证新记忆基本可用。

## 2\. 文件变更监听（没有编辑的这个功能，忽略）

监控 json 文件 MD5 哈希变更，用户手动编辑文件时，自动触发增量同步，更新向量库。

## 3\. 定时兜底校验

比对向量库数据，以 json 真相源为准，补全缺失向量、修复异常数据，解决宕机、断网导致的同步断层问题。

系统元数据维护一个同步记录checkpoint，每次从checkpoint开始对比。

checkpoint在写入完数据库时更新

## 4\. 并发安全保障

多实例并发读写文件时，加分布式锁，防止文件内容错乱、覆盖冲突。
