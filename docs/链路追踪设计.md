# 链路追踪设计（全链路 Trace 与评测数据基座）

trace 模块是项目的统一观测基座：一次记录同时服务三个消费方——在线告警（Prometheus）、
离线评测（eval 脚本）、admin 监控页面。数据源唯一（PostgreSQL schema=`telemetry`），
不双写、不部署独立观测平台。

设计参考生产主流（Langfuse trace→observation 树、OTel GenAI 语义约定），
规模按数百张表设计（载荷截断、retention、异步批量写），追踪故障只降级、不阻断主链路。

## 1. 架构

```
流程点直调 + 统一出口直埋（观测不寄生 hook 通道）
  turn/session 生命周期：auto_plan_manager / chat_service 直调
  llm span：LLM 韧性层（resilient_invoke / resilient_invoke_stream）
  tool/retrieval span：tool_executor（注册表 obs_category 决定 op_type，只记骨架）
  agent / compaction：调用方 start_span 主动埋点
  后台任务（session_summary 提取）：background_trace 独立 root trace（memory 不落 trace）
                       │
                       ▼
        trace 生命周期与 TurnBuffer（recorder，contextvars 维护 turn 绑定 + parent 栈 + agent 名栈）
          │       │ turn_end 收口 flush / background_trace 收口 / session_end 兜底 flush
          │       ▼
          │     TraceStore ──异步批量──► PostgreSQL（schema=telemetry）
          │                              traces / trace_spans / tool_semantics / trace_scores / eval_*
          │                                 │
          ▼                                 ▼
   Prometheus 指标（metrics.py）    admin 查询（query_service → /stats/admin/*）
   告警（prometheus_alerts.yml）    离线评测（eval.py：tool_semantics 取 SQL + trace_scores 回写）
```
采集入口全部为直调/直埋：span 在执行点 with 包裹产生（天然配对、parent 天然正确），
turn 聚合（tokens/主力模型/工具数）在 turn_end 收口时从 spans 派生（单一来源）；
与 Prometheus 有关的指标在埋点处直接喂入。
工具语义数据（sql/recalled_tables 等）经 AFTER_TOOL_CALL 监听器单独落 tool_semantics
（骨架/语义分表）。TraceStore 异步批量刷到 Postgres 库中。


## 2. 模块结构（backend/src/codegenx/ai_service/trace/）

| 模块 | 职责 |
|---|---|
| recorder | turn/session 生命周期直调函数（turn_start / turn_end / turn_error / session_start / session_end）+ TurnBuffer 管理；turn 聚合在 turn_end 从 spans 派生；喂 turn/session 级 Prometheus 指标 |
| api | 主动 span API：`start_span`（上下文管理器，agent span 进入时维护 agent 名栈）、`SpanHandle`（set_output / add_attributes / set_status / discard）、`add_turn_tags`（评测注入）、`report_context_usage`（上下文占用上报）、`current_app_id`（token 计数 app_id 归因） |
| context | contextvars：turn 绑定、parent 栈、agent 名栈（`get_current_agent`——llm span 归属） |
| store | asyncpg 批量落库，失败重试后丢弃记日志 |
| metrics | Prometheus 指标唯一出口 + StreakTracker（工具连续失败、上下文连续超限） |
| query_service | admin 监控查询，asyncpg 直连 telemetry 派生（响应契约不变） |
| maintenance | retention 定期清理（telemetry 表 + chat_message） |
| schema/admin | admin 响应模型（camelCase 序列化，含 span 树节点模型） |

## 3. 数据模型（init/telemetry_schema.sql，schema=telemetry）

| 表 | 职责 | 关键字段 |
|---|---|---|
| traces | 一轮请求的根 | trace_id PK, session_id, app_id, user_id, db_name, agent, input, output, status, error, model, prompt_tokens, completion_tokens, duration_ms, started_at, tags JSONB |
| trace_spans | span 树（执行骨架：谁在何时调了什么、多久、成败） | span_id PK, trace_id, parent_span_id, session_id, turn_id(request_id), op_type, name, agent, seq, started_at, duration_ms, status, error, input/output JSONB |
| tool_semantics | 工具语义数据（评测/归因消费，与骨架分家） | trace_id, session_id, turn_id, span_id, tool_name, success, attributes JSONB(sql/datasource/row_count/rows_preview/recalled_tables), created_at |
| trace_scores | 评分/反馈 | trace_id, name(user_feedback/llm_judge/EX/VES/valid_sql), value, comment, evaluator, created_at |
| eval_datasets / eval_cases | 金标准题集 | question, gold_sql, difficulty, ops, grain, multi_hop, status(draft/verified) |

- traces.tags：`tool_calls`、`context_usage`（turn 聚合）+ 外部注入（`eval_set` / `case_id` / `agent_version`）；注入项仅作过滤线索，评估结果一律落 trace_scores（可回写、可重算，与 append-only 的 traces 生命周期分离）
- 索引：trace_spans(trace_id)、(session_id, started_at)、(op_type, started_at)；traces(started_at)、(session_id, started_at)；按月分区预留

## 4. span 类型与埋点

| op_type | 记录内容 | 来源 |
|---|---|---|
| turn | 单轮根：status、tokens、耗时、errors | 流程点直调（auto_plan_manager：turn_start / turn_end / turn_error） |
| agent | 智能体执行边界：request_id/dispatched_by/task_id/step_id/steps、success、result_chars | 主动 span（base_react_agent.run） |
| llm | messages 输入、completion/tool_calls 输出、attributes（model/finish_reason/prompt/completion tokens——turn 聚合派生的单一来源）；每次实际 API 调用一个 span（含失败重试） | LLM 韧性层直埋（resilience：resilient_invoke / resilient_invoke_stream，name 取当前 agent 域） |
| tool | 执行骨架：tool_name、arguments、输出概要、success/error | tool_executor 直埋（语义字段由 AFTER_TOOL_CALL 监听器落 tool_semantics） |
| retrieval | 语义层检索工具骨架：query、输出概要、success/error | tool_executor 直埋（注册表 obs_category=retrieval） |
| compaction | 压缩边界，两类：token_budget（预算账目 total_budget/tokens 前后/evicted_*/compact_path/truncated/sections/context_usage）、session_summary（摘要触发） | 主动 span |

埋点原则：

- **统一出口直埋**：llm span 在 LLM 韧性层、tool/retrieval span 在 tool_executor、turn/session 生命周期在流程点直调——with 块天然配对（无 before/after 配对状态机）、parent 天然正确、AFTER 事件 PARALLEL 分发下 span 顺序安全
- **通道分工**：hook 承担决策（拦截/注入/护轨包裹）与业务信号，trace 承担观测基线（谁在何时调了什么、多久、成败）；hook 通道里不允许没有决策权的监听器（决策权 = blocked/inject 改写或业务信号消费），观测数据不寄生 hook 通道；观测监听器绝不抛错、不进决策链路
- **骨架/语义分表**：span 骨架（id/parent/时长/status/输入输出概要）由埋点产生；业务语义字段（sql、recalled_tables、rows_preview 等评测归因数据）经 AFTER_TOOL_CALL 监听器（hook/tool_semantics.py）写 telemetry.tool_semantics 独立表——生命周期分家（语义数据长期保留，trace_spans 受 retention 清理）、消费方分家（eval 脚本 vs 观测），span_id 关联两侧
- **主动 span 只补边界**：agent 边界与压缩边界由调用方（base_react_agent、session_context）用 `start_span` 埋点；compact 模块本身零 trace 依赖
- **无实际动作不落 span**：token_budget 仅实际压缩（微压缩/摘要/驱逐/截断/瘦身）时保留，纯预算分配 discard；session_summary 未过提取阈值不记录（触发即记，提取在后台异步完成）
- **span 树形态**：turn → agent(leader) → { llm、tool(dispatch_agent) → agent(子)、compaction }；session_summary 以 root=True 直挂 turn

## 5. 上下文传播与占用上报

- contextvars 维护 turn 绑定 + parent 栈 + agent 名栈：span with 块入栈/退栈（兄弟 span 不串联），llm span 的 name/agent 取当前 agent 域（`get_current_agent`）
- 工具执行 with 块内派发的子 agent / llm span 自动挂该 tool span 下（gather 并行任务继承 context 副本，任务内 set 不污染外层）
- `report_context_usage`：上下文占用每 step 上报，与 span 解耦——回写 turn 聚合 tags.context_usage + 喂连续超限 streak（span 丢弃不影响 streak 计数）
- `add_turn_tags`：评测框架 replay 时注入 eval_set/case_id/agent_version，支撑版本回归对比
- 后台任务（session_summary 提取）用 `background_trace(trigger, ...)` 建独立 root trace（agent=trigger、tags.background 标记、turn 根 span）：块内 llm span/token 指标自动归属，token 归因真实 app 而非 system；正常退出收口 flush，业务异常透传且 trace 置 failed
- memory 调度不落 trace：turn 结束只投递信号，实际提取是跟随 session 的后台任务，`memory_tasks` 任务表（心跳/mark_done/mark_failed）+ 专属指标（memory_extract_*）已可监控；其 LLM 调用仍计入 `llm_calls_total{trigger=memory_*}`
- 后台任务晚于 turn_end（buffer 已收口）时，span 直接 enqueue 落库不丢

## 6. Prometheus 指标与告警

- 指标定义与喂入唯一出口 `trace/metrics.py`：LLM token 计数（prompt/completion）喂入点在 LLM 韧性层（`_record_usage`，app_id 按 turn 上下文归因——在线轮次/后台 trace=真实 app、无绑定=system，同一次调用不双计数）；LLM 调用计数（含失败分类）由韧性层每次 attempt 喂 `_record_call` → `feed_llm_attempt`（`llm_calls_total{app_id, model, trigger, outcome}`——trigger=触发来源（agent 名/后台组件名，指标可答「什么触发的这次调用」），延迟/首 token 仅成功收口时 observe）；工具调用由 tool_executor 喂入；turn/session 计数由生命周期直调函数喂入
- 指标：LLM 调用（trigger/outcome 维度）/延迟分布/首 token/最近单次延迟、token 计数、工具调用、turn/session 计数
- streak gauge：工具按工具名全局连续失败（跨会话、任一次成功清零，为后续工具下线铺路）；上下文按会话内部计数、gauge 上报跨会话最大值（不带 session_id label，避免 Prometheus 序列随会话数无限膨胀，会话明细见 streak≥3 日志）
- 告警由 Prometheus alert 栈承接（infra/monitoring/prometheus_alerts.yml：LLM 平均延迟、单次超时、工具连续失败、上下文连续超限，均按数值比较、不依赖 label 维度）；admin 告警列表端点恒返回空分页

## 7. admin 监控 API（/stats/admin/*，管理员角色）

- overview / sessions（过滤分页）/ session detail / turn detail（含工具调用明细）/ token usage
- turn span 树端点：返回扁平 span 列表 + 服务端计算 offsetMs，前端渲染瀑布图
- 数据全部从 telemetry 派生（asyncpg 直连），响应模型 camelCase 契约

## 8. 评测闭环

```
eval_cases（金标准题集） ──replay──► POST /ai/chat/gen（每题独立会话 + add_turn_tags 注入标识）
                                        │ 在线链路自动落库
                                        ▼
tool_semantics（execute_postgresql 语义行：attributes.sql / datasource / success）
   → score 读库取最后一次 SQL 尝试判 Valid，最后一次成功 SQL 判 EX/VES
   → 连业务库执行 pred/gold 结果集对比
   → 写回 trace_scores → report 聚合输出（总览/失败归类/维度分组）
```

- 工具：`data/evaluate/eval.py` 四个子命令（import-cases / replay / score / report）
- 失败归类：no_sql / sql_error / result_mismatch / db_unknown / gold_error
- 用户点赞/纠错 → trace_scores(name=user_feedback) → verified query 沉淀（语义层反馈闭环）

## 9. 可靠性与清理

- 主动 span 无 turn 绑定或 trace 禁用时 no-op，绝不抛错；with 块异常自动置 error 后原样上抛
- 落库失败重试后丢弃并记日志（追踪故障只降级）
- 载荷截断配置化：文本单字段上限（默认 32KB）超长截断标 `truncated`；rows_preview 默认 20 行；captureContent 可关内容只留元数据
- retention：maintenance 定期清理超期 telemetry 数据与 chat_message

## 10. 配置

- `backend/.env`：复用 POSTGRES_* 元数据库连接
- `backend/config.json → trace`：enabled / payloadMaxChars / rowsPreviewLimit / flushBatchSize / retentionDays / captureContent

## 11. 明确不做

- 不自建/不部署 Langfuse 等独立观测平台（单实例、单消费方，PG 足够）
- 不引入 Kafka/ClickHouse（日 trace 量级 10⁴ 内，量级到 10⁶+/天再评估）
- 不双写两套指标（Prometheus 指标与 telemetry 落库同源喂入）
- 不做实时联邦查询/全量 prompt 永久存储（截断 + retention 配置化）
- 不引入 OpenTelemetry SDK / collector：单进程嵌入式观测，trace 与业务表同库 join（评测回写、tags 注入）是核心价值，OTel 导出到独立后端会断裂 join 且新增 collector 运维；span 属性命名保持对齐 OTel GenAI 语义约定，为未来多服务拆分或接 Langfuse（ingestion 走 OTel）留迁移缝

## 12. 演进 TODO（方向已定，未排期）

2. **waterfall 护轨与 span 桥接**：输入输出护轨/安全校验落地走 waterfall 洋葱分发（hook/core.py 已预留，BEFORE/AFTER_LLM_INVOKE 事件已保留为零监听器挂载点）；护轨层耗时/拦截经 set_trace_sink 桥接为 telemetry span 挂当前 parent，进入 trace 树。桥单向（hook → trace）：hook 的 Span 机制只追踪 hook 层自身执行，业务执行树始终由 trace contextvars 承担（HookContext 生命周期只有一次事件分发，结构上无法跨分发传播）
