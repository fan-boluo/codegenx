# 上下文工程设计方案

Agent 每次调用 LLM 的上下文由四部分组成：**system prompt、记忆注入、项目元数据、对话历史**。本方案围绕两个核心问题展开：**防止上下文膨胀**与**保证对话连续性**。

设计总原则：**分层存储，真相与视图分离**。

```
┌─────────────────────────────────────────────┐
│              Context Assembler               │
│   （统一预算分配器，每次调 LLM 前组装上下文）    │
└──────┬──────────┬──────────┬────────────────┘
       │          │          │
  ┌────▼────┐ ┌───▼─────┐ ┌──▼──────────┐
  │ 追加日志  │ │ 压缩视图 │ │ Offload 仓库 │
  │ (真相源)  │ │ (可重建) │ │ (工具结果原文)│
  └─────────┘ └─────────┘ └─────────────┘
```

| 存储层        | 内容                              | 特性                          |
| ---------- | ------------------------------- | --------------------------- |
| 追加日志       | 完整对话消息流（messages.jsonl）         | 逐轮 append，永不有损修改，crash-safe |
| 压缩视图       | 结构化摘要 + 水位线（summarized\_up\_to） | 可随时从日志重建，属于缓存               |
| Offload 仓库 | 被移出上下文的工具结果原文                   | 内容寻址（hash），可设 TTL/LRU 淘汰    |

## 1 防止上下文膨胀

### 1.1 各部分 Token 限制与统一预算分配

各部分（记忆注入、对话历史、项目元数据）分别设上限之外，引入**统一预算分配器**做总控——各部分各自不超限不等于总量不超限。

* **总预算** = 模型窗口 × 0.85（预留输出 max\_tokens 与安全余量）；
* 每个区域设**软限 / 硬限**两级阈值；
* 超预算时按**固定驱逐优先级**让位：

```
工具结果原文 → 中段历史 → 记忆注入 → 会话摘要
（system prompt + 最初任务消息 + 最近 N 轮：永不驱逐，pin 住）
```

* 驱逐不是删除，而是**降级为占位符**——原文仍保留在追加日志 / Offload 仓库中，可随时回捞。

### 1.2 三层压缩策略

#### L1：工具结果卸载（Offload，替代有损微压）

调用 LLM 前，对早期历史中体积大的工具执行结果（read/write/bash 输出等）做卸载。关键区别于"有损压缩"：**不是删掉，而是搬到仓库并留取件码**。

触发规则：工具结果距今超过 K 轮，或体积超过阈值。流程：

1. 工具执行产生结果时**立即落盘**到 Offload 仓库，得到句柄 ID（内容寻址，同内容天然去重）；
2. 上下文中替换为结构化占位符：`{工具名, 关键参数, ≤200 token 摘要, 句柄ID}`；
3. 为模型提供 `recall_tool_result(id)` 工具，需要细节时按句柄回捞原文。

这样可避免经典翻车场景：用户说"把刚才读的那个文件第 30 行改一下"，而文件内容已被压掉。

#### L2：每轮结束后增量摘要

每轮会话结束后，根据上下文长度判断是否触发摘要任务：

* 摘要**始终从原始日志增量生成**：`旧摘要 + 水位线之后的新消息 → 新摘要`，不做"摘要套摘要"，避免多轮压缩后的误差累积与细节漂移；
* 摘要采用**结构化模板**而非自由文本，保证关键信息不被"摘要掉"：

```
任务目标 / 已确认决策 / 硬约束 / 涉及文件清单 / 未完成事项 / 关键数值
```

* 摘要生成本身带 **max\_tokens 硬约束**，防止摘要输出过长反过来触发 PTL；
* 摘要写入与水位线（summarized\_up\_to offset）更新**原子完成**。

#### L3：调用 LLM 前的检查与替换

组装上下文时根据预算判断：

* **已有会话摘要**：用"摘要 + 水位线之后的未压缩原始消息"组装；
* **没有摘要**：现场触发 LLM 压缩（同步等待，或按 1.3 兜底）。

### 1.3 兜底设计（保证收敛）

```
PTL（prompt too long）
  → 减半待压缩范围，循环重试（最多 N 次）
  → LLM 调用失败 → 降级截断：
      保头（system + 最初任务定义）+ 保尾（最近 N 轮）
      中段替换为占位符（原文在日志中，可回捞）
  → 标记 degraded，冷却 10 分钟
  → 基于完整日志重新 LLM 压缩，恢复视图
```

要点：

* **PTL 重试必须保证收敛**：每次减半 + 最大重试次数 + 确定性落底（保头保尾截断），任何路径的最终输出都确定性地 fit 进窗口；
* **降级截断绝不简单掐头**——最前面的任务定义与用户原始需求是最不能丢的；
* **"恢复"成立的前提**是原始日志完整（见第 2 节）：截断只影响视图，不影响真相源，因此降级是可逆的。

## 2 会话连续

目标：用户一周后重新打开会话仍可无损续聊。核心手段：**逐轮追加日志（真相源）+ 轻量视图快照（恢复入口）**。

### 2.1 逐轮追加日志（替代终态全量快照）

* 每轮对话结束**立即 append** 到 `messages.jsonl` 并 fsync——进程崩溃、机器重启最多丢一轮，而不是丢整个会话；
* 日志只追加、不改写，是唯一真相源；
* 避免"会话结束才全量快照"的两个问题：崩溃丢数据窗口、全量重写 O(n) IO 与半写损坏（如需全量文件，用 temp + rename 原子写）。

### 2.2 视图快照

在会话结束或空闲超时时，额外落一个**轻量视图文件**（它是缓存，不是真相）：

* 最新结构化摘要 + 水位线；
* Offload 句柄索引；
* **环境指纹**：cwd、git commit、关键文件 hash、最后交互时间戳。

### 2.3 会话恢复流程

重新打开 session 时：

1. **加载视图而非全量日志**：最新摘要 + 水位线之后的原始消息 + Offload 占位符，长会话也能秒开；
2. **校验环境指纹**：若文件已变更或距上次交互超过阈值（如 24h），注入系统提示："距上次交互已过 N 天，以下文件已变更：…，请先确认任务状态是否仍然有效"，避免模型基于过期的世界状态继续执行；
3. **与长期记忆对齐**：会话结束/压缩时，从摘要中提炼值得跨会话的事实写入长期记忆，避免会话内历史与全局记忆冲突。

### 2.4 压缩与用户输入的并发一致性

每轮结束后的摘要任务是异步的，用户可能秒回下一条消息：

* 视图带版本号 + 水位线；组装上下文时按**当前已确认水位线**取用（水位线之前的消息永远可安全替换为摘要）；
* 压缩任务未完成也不阻塞用户、不会带着未压缩的超长上下文调 LLM；任务完成后新水位线自然生效。

## 3 可观测与评估闭环

* **线上指标**：PTL 触发率、压缩失败/降级率、摘要压缩比、Offload 回捞命中率、会话恢复成功率；
* **质量评估**：离线回放——对同一长会话，比较"全量上下文"与"压缩后上下文"回答关键事实问题的一致性（LLM-as-judge 打分），作为摘要模板与压缩策略迭代的依据。
