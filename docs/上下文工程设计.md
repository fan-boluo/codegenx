# 上下文工程设计
> 2026/10/29 整理
本文档描述系统**当前的**上下文工程设计，以 `ai_service/context/` 的上下文对象为主，
串联预算分配（`compact/`）、会话摘要、会话持久化与子智能体链路的协作方式。
文末列出已识别但暂不实施的扩展项。

---

## 1 总体设计

设计总原则：**分层存储，真相与视图分离；逐层管控上下文规模**。

### 1.1 上下文对象

| 对象 | 文件 | 职责 |
| --- | --- | --- |
| `CommonContext` | `context/common_context.py` | 上下文基类：`chat_messages` 工作列表、`assemble()`组装、通用工具结果压缩、获取任务看板 |
| `SessionContext` | `context/session_context.py` | leader 的会话真相源：跨轮历史、初始化快照/摘要注入、压缩、摘要提取、摘要水位、上下文token信息 |
| `SubContext` | `context/sub_context.py` | 子智能体一次性工作区：仅清空 + 继承通用压缩，无摘要水位、无快照/恢复 |
### 1.2 单次 LLM 调用的消息组成

```
messages = [system] + payload_messages
```
- BaseReactAent._prepare_agent 进行工具解析，system_prompt参数准备，chat_messages初始化
- 各部分预算管理：`CompactionService.token_budget()`
- 最后`assemble()`组装

### 1.3 存储分层

chat_messages:执行过程中的原始消息，内存
last_chat_snapshot_{session_id}.jsonl：快照，每轮结束的全量消息列表
SUMMARY.md：摘要，turn结束后检查执行，记录水位，用于step执行中快速替换，和chat_messages初始化替换
工具执行结果落盘：暂时没做还

| 存储层 | 内容 | 特性 |
| --- | --- | --- |
| 内存 `chat_messages` | 当前会话全量消息流（含 tool_calls / tool 结果） | turn 内唯一真相源 |
| turn 快照 `last_chat_snapshot_{session_id}.jsonl` | 每轮结束的全量消息列表（JSON 数组整文件重写） | swap-out / 会话恢复的数据源；由 `SessionPersistence.save_turn_chat_message_snapshot()` 写入、`get_turn_chat_message_snapshot()` 读取 |
| `SUMMARY.md` + `summary_state.json` | 会话摘要 + 内存 index 水位/阈值状态 | 摘要属缓存视图；水位状态随摘要推进/压缩重置落盘，缺失摘要时回退全量重摘 |
| `chat_message` MySQL | user 消息与终答 assistant 消息（tool 消息不落表） | `ChatMessageStore.append_message()` 分配会话内单调 `seq`；超 32KB 原文外置 `message_blobs/{session}/{seq}.json`；供前端历史与记忆漏斗消费 |
| `tool_log_*.jsonl` | 工具调用轨迹| `tool_log` 由 `AFTER_TOOL_CALL` hook 追加；|
| `{tool_call_id}_persist.txt` | 大工具结果原文（`compact/large_output.py`） | 当前未接线，见 §8 |

目录统一为 `.data/{userId}/{appId}/session/{sessionId}/`（`shared.constants.get_current_session_dir()`）。

## 2 上下文规模管控

### 2.1 预算入口

`BaseReActAgent._run_impl()` 每个 step 执行：

```
_refresh_step_params(request_id)：更新system_prompt中的可变参数
→ CompactionService.token_budget()：预算总控
→ CommonContext.assemble(payload.payload_messages)（组装：system 前置，产出的 messages 传给 think）
→ report_context_usage() 上报token
```

- `context_max_tokens`总预算 取当前 agent 的 `AgentConfig`（leader 与子智能体各自独立）；
- **总预算** = `context_max_tokens × config.compact.context_budget_ratio`（默认 0.85，预留输出与安全余量）；
- **tools 子预算** = 总预算 × `config.compact.tool_budget_ratio`（默认 0.15）；
- 结果 `ContextBudgetResult` 记录 tokens 前后、驱逐计数、分区报告、`compact_path`、`truncated`；
  `compacted` 为真时才写 `compaction/token_budget` trace span。

### 2.2 驱逐级联

每次调用先执行 `CommonContext.normalize_messages()`（无条件）；若仍超限，按以下顺序逐级处置，
每级执行前重新判超限，达标即停：

| 级 | 方法 | 作用对象 | 说明 |
| --- | --- | --- | --- |
| 前置 | `CommonContext.normalize_messages()` | 真相源 | `normalize_history()` 标准化字段 + `drop_orphan_tool_pairs()` 清理不完整 tool 配对 |
| 1 | `CommonContext.micro_compact()` | 真相源（就地替换） | 工具结果微压缩，见 §2.3 |
| 2 | `CommonContext.compact()`  | 真相源（重建列表） | 消息摘要压缩，见 §2.4；消息预算不足 `MIN_TOKENS_AFTER`(200) 时跳过 |
| 3 | `enforce_budget_inplace()` | 真相源（占位降级） | 历史驱逐，见 §2.5 |
| 4 | `_keep_last_n_messages()` | 仅 payload 视图 | 保尾硬截断，见 §2.6 |
| 5 | 分区驱逐 + `compress_tool_catalog()` | 仅当次 system / tools | 见 §2.7 |

**真相源策略**：

- 第 1/3 级就地修改 `context.chat_messages`，列表长度不变 → 摘要水位 `extract_msg_idx` 保持有效；
- 第 2 级重建列表 → 由 `SessionContext.compact()` 重置水位（Path A=2 / Path B=0）并落盘；子agent没有摘要直接压缩Path B
- 第 4 级只截 payload 视图，被截消息仍留在真相源，可被 turn 末摘要提取，闭环不破；
- 历史占位消息对模型无信息量，payload 视图剔除，真相源保留以对齐水位；
- system 分区驱逐只影响当次 `system_prompt`，不回写 profile；tools 瘦身只影响当次目录。

### 2.3 微压缩（`microcompact_messages()`）

- 触发门槛：消息总 token ≥ `AUTOCOMPACT_THRESHOLD × 0.6`（全局默认窗口口径，见 §8）；
- 工具结果超过 `compact.max_tool_result_tokens`（默认 3000）→ 替换为 `[Old tool result content cleared]`；
- 只处理 `COMPACTABLE_TOOLS`（读写文件、shell、grep 等）；
- 最近 `compact.protect_last_n_results`（默认 5）个工具调用受保护；
- `CLEAR_TOOL_INPUTS`（`write_file`）的 assistant 参数同时降级为 `{path, note}`，
  避免整文件内容滞留在参数里；
- 纯消息变更，不调用 LLM，不改变消息条数。

### 2.4 摘要压缩（`CompactionService.compact_if_needed()`）

进入条件：`should_auto_compact(messages, threshold=消息预算)` 为真，且
`tokens_before > MAX_TOKENS_AFTER`（1200）；短对话直接交给后续驱逐/截断，避免空耗摘要调用。

两条路径（`_run_compaction()`）：

- **Path A（`_session_memory_compact()`，leader 专属）**：经 `summary_loader` 读取 `SUMMARY.md`，
  按 `summary_watermark` 截掉已覆盖前缀，合成 `[user 摘要, assistant 确认]` 对 + 尾部保留；
  不经 LLM，零成本；
- **Path B（`_llm_compact()`，leader / 子智能体）**：`BASE_COMPACT_PROMPT` 交给压缩小模型
  （`compact.model_name`，经 `resilient_invoke` 熔断/重试/降级），输出结构化摘要替换历史；
  输出 `max_tokens = MAX_OUTPUT_TOKENS_FOR_SUMMARY`（≤500）防止越压越长；
- 尾部保留统一由 `_keep_last_n_messages()` 执行，预算优先用调用方 `token_budget`（封顶 `MAX_TOKENS_AFTER`）。

失败统一出口：

- Path A 读取失败 → 降级 Path B，不直接兜底；
- Path B 调用失败 / 空摘要 / 压缩后 token 不降反升 → `_keep_last_n_messages()` 保守截断，
  返回 `path_used="none"`，绝不向上抛错；
- 压缩无效属业务结果，不进熔断（模型故障由韧性层模型级熔断记录）。

压缩成功后 `SessionContext.compact()` 清理 `SUMMARY.md`（Path A 内容已融进合成对；
Path B 摘要与旧水位已对不上），重置 `tokens_at_last_extract` 并 `save_state()` 落盘。

### 2.5 历史驱逐（`enforce_budget_inplace()`）

- 分区语义：最后一条 user 之前的中段历史（只降级 assistant 文本）、最后一条 user（当前任务，永不驱逐）、
  之后的 ReAct 循环区；
- 优先级：工具结果原文 → 中段 assistant 历史；
- 工具结果保护最近 `compact.protect_last_n_results` 条；
- 降级为占位符（`TOOL_PLACEHOLDER` / `HISTORY_PLACEHOLDER`），幂等跳过已占位消息；
- 工具结果可重新调用回捞，中段历史原文在快照中可回捞。

### 2.6 保尾硬截断

`_keep_last_n_messages()` 从尾部保留尽可能多的消息：至少保留 `MIN_TEXT_MESSAGES`（5）条有文本内容的消息，
累计超过 `MIN_TOKENS_AFTER`（200）后才允许提前停止；结果经 `drop_orphan_tool_pairs()` 后仅替换 payload 视图。

### 2.7 system 分区与 tools 瘦身

分区驱逐顺序（`SECTION_EVICTION_ORDER`，越靠前越先走）：

```
skill_prompt → memory_prompt → resource_prompt → expand_prompt
→ taskbord_prompt → examples → tool_schema
```

- 被驱逐分区原位留短占位（`section_evicted_placeholder()`），模型可感知并尝试用工具重新加载；
- 空态分区（占位比原文还大）跳过；
- `tool_schema` 是 function calling 契约：`compress_tool_catalog()` 只做描述层降级，不删工具：
  ① 截断工具描述（`tool_description_max_chars`，默认 240）→ ② 剥离参数级 description →
  ③ 描述压到 80 字符；仍超预算则保留全部工具并告警。

### 2.8 LLM 超长恢复与工具结果上限

- 流式调用 `invoke_stream_with_revovery()`：`classify_llm_error()` 判为 `CONTEXT_OVERFLOW` 时
  调 `agent_context.compact()`（多态：leader Path A / 子智能体 Path B）→ `assemble()` → 重试，
  上限 `AgentConfig.max_compact_attempts`（2）；
  `finish_reason=length/max_tokens` 时注入续写消息重试，上限 `max_continuation_attempts`（3）；
- 非流式 `think`（`resilient_invoke`）当前无上下文超长恢复，列入扩展（§8）；
- `ToolExecutor.dispatch_tool_calls()` 对单个工具结果做 `MAX_TOOL_RESULT_CHARS`（8000 字符）截断，
  超出部分当前不可回捞（见 §8）。

## 3 会话摘要

会话摘要服务：`SessionSummaryService`（`compact/session_summary.py`），
阈值状态与判定谓词由 `SessionContext.summary_state: SummaryState` 持有。

### 3.1 触发阈值

`SummaryState.should_extract()`：

- 上下文 < 6000 tokens 时不跟踪（`MIN_TOKENS_TO_INIT`）；
- 上次提取后 token 增长 ≥ 150（`MIN_TOKENS_BETWEEN_UPDATES`）才允许再次提取；
- 且新增消息数 ≥ 4（`MIN_MESSAGES_BETWEEN_UPDATES`）或增长 ≥ 450（150 × 3）；
- `extracting=True` 时永不重叠。

### 3.2 提取与水位

`SessionContext.session_summary_extract()`（turn 结束调用）→ `SessionSummaryService.fire_extract()`：

- 非阻塞：`note_trigger()` 记录 token 基线后 `asyncio.create_task(_extract(...))`，快照浅拷贝传入；
- `_extract()`：按 `extract_msg_idx` 内存 index 水位切增量，截到「assistant 收尾」的完整前缀
  （停止/异常留下的半轮留待下次），单次上限 `compact.summary_extract_max_messages`（默认 200），
  超出部分下轮补摘；
- `_summarize()`：结构化模板（Session Title / Current State / Task Specification /
  Key Files and Topics / Errors and Corrections / Learnings / Key Results / Worklog），
  `temperature=0.0`、`max_tokens=4096`，经 `resilient_invoke`；
- `_format_messages_for_extraction()` 只喂 user/assistant 文本（单条截断 400 字符）与 assistant
  `tool_calls` 的 name/input，tool 结果原文不进摘要（结论由 assistant 文本承载）；
- 原子序：先覆盖写 `SUMMARY.md` 成功，再推进 `extract_msg_idx` 并 `save_state()`——
  失败只会重复摘要，不会漏摘要；
- 失败非致命：LLM 异常 / 空输出 / 结构异常 → 旧摘要与水位保留，等下次阈值触发；
- 水位失效（`extract_msg_idx > len(snapshot)`，如压缩重建出更短列表）→ 回退 0 全量重摘；
  水位恰好等于列表末尾 → 无新消息，直接返回；
- 文件：`SUMMARY.md` 与 `summary_state.json`（`extract_msg_idx` / `initialized` /
  `tokens_at_last_extract`），路径见 `get_session_summary_path()` / `get_session_summary_state_path()`。

### 3.3 摘要注入与替代

摘要不以 system 变量注入，而是以「合成 user/assistant 对」进入消息列表：

- **turn 开始恢复**：`SessionContext.init_chat_messages()` →
  `_restore_summary_state()` 还原水位 → `_inject_summary_from_file()`：
  有 `SUMMARY.md` 时按水位截掉已覆盖前缀，prepend `SessionSummaryService.build_summary_injection_pair()` 合成对，
  水位重置 2、基线重估，随后 `clear()` 同时删除 `SUMMARY.md` 与 `summary_state.json`
  （合成对已进入消息列表，防止下次再注入；后续提取从新列表重新建立水位）；
  无摘要时不截、水位归 0（宁全量重摘，不丢内容）；
- **压缩 Path A**：`_session_memory_compact()` 用同一语义把摘要替代已覆盖前缀。

### 3.4 卸载前保证

swap-out 与 idle 回收前调用 `SessionContext.ensure_summary_before_unload()`，
绕过增长阈值强制触发一轮 `fire_extract()`；fire-and-forget，后台任务持内存快照独立落盘，
清理锁内不做 DB 读与 LLM 调用。

### 3.5 一致性与已知损失

- 写者：`SUMMARY.md` 只由后台提取任务写入；`summary_state.json` 由提取任务推进、
  `_inject_summary_from_file()` 与 `SessionContext.compact()` 重置共同写入，
  `extracting` 防止同会话提取任务重叠；
- 水位是内存 index（非 DB seq），仅对当前快照列表形态有效；压缩重建后由 Path A=2 /
  Path B=0 重置并落盘；
- 摘要只覆盖 user/assistant 文本与工具调用轨迹的结论，不替代 tool 原文；
- **已知损失（权衡，暂不修）**：跨轮恢复时只保留 user/assistant 文本，
  empty-content 的 assistant `tool_calls` 消息被整条丢弃 → 下轮看不到「上一轮调用过哪些工具、
  参数与成败」这份操作台账，只能盲猜或重调（有微重复成本，无正确性错误）。

## 4 会话连续

### 4.1 turn 生命周期

```
请求到达 ChatService
  → _restore_session_history()（内存为空时从快照回填）
  → user 消息入库 chat_message（append_message 分配 seq）
  → 入队 → AutoPlanManager.execute_request()
      → context_manager.add_user_message()
      → LeaderAgent.run() → _prepare_agent(request)
          → init_chat_messages()：去末条（当前请求）、恢复水位、摘要替代、过滤 tool
          → _run_impl() 追加 task_text，进入 ReAct 循环
      → 终答由 leader 文本留在 chat_messages，_persist_assistant_message() 落 chat_message
  → finally：
      ① session_summary_extract()（后台摘要）
      ② save_turn_chat_message_snapshot()（全量快照落盘）
```

- ReAct 循环中 assistant（含 tool_calls）与 tool 结果只追加到 `chat_messages`，不落 `chat_message` 表；
- 表内完整轮次 = user 行 + assistant 终答行，供前端历史与记忆 warm_extract 使用。

### 4.2 swap-out 与空闲回收（`SessionPool._cleanup_inactive_sessions()`）

- **swap-out**：空闲超过 `session.swap_idle_seconds` 且 `_is_quiescent()` 为真 →
  `ensure_summary_before_unload()` → 清空 `chat_messages`，会话对象留在池中；
- **idle 回收**：空闲超过 `session.idle_timeout_seconds` 且无在途任务 →
  `ensure_summary_before_unload()` → 从池中删除；
- 执行中的会话不回收，避免误杀长任务；已关闭会话不做摘要补偿。

### 4.3 会话恢复

`ChatService._restore_session_history()` 在内存 `chat_messages` 为空时按 turn 快照回填，
swap-out 复用与空闲回收后新建两条路径统一处理；随后下次 `run()` 由
`init_chat_messages()` 消费摘要水位并重建可发送历史。

### 4.4 跨轮过滤规则

`SessionContext.init_chat_messages()` 的顺序约束（水位语义要求，必须先消费再过滤）：

1. 去末条：本轮请求原文由 `run()` 以 `task_text` 补回；
2. 恢复水位 + 摘要替代：必须在全量空间（含 tool）完成；
3. 过滤 tool：只保留 `role in (user, assistant)` 且 `content` 非空的消息，只拷 `role/content`。

先过滤后用水位会导致 index 跨列表形态不可比：防御回退会重摘合成对（套娃），
水位虚高则部分消息「冒充已摘要」永远不进 `SUMMARY.md`，随后被压缩丢弃。

**设计依据**：

- 只拷 `role/content`，assistant 的 `tool_calls` 不会存活，天然规避
  「有 tool_calls 无 tool 结果」的 API 400 错；
- tool 结果是主流设计中优先牺牲的信息（体积大、可重调回捞、结论已进 assistant 文本与摘要）；
- 原文可回捞：工具结果可重新调用工具获取。

## 5 子智能体上下文策略

### 5.1 派发链路

`DispatchAgentTool.execute()`（工具名 `dispatch_agent`）是 lead 的编排工具
（由 `config.json agents[].tools` 白名单控制可见性）：

- 调用即**同步执行**目标子智能体的完整 `run()`，最终文本作为 tool result 回填 lead 对话；
- 每次派发新建独立 `SubContext`，与 lead 的 `SessionContext` 完全隔离；
- lead 只掌握子智能体清单的 `name - desc`（`agents_list_desc()`），**task 必须自包含**：
  子智能体看不到会话历史，目标、文件路径、口径约束都要写进 task；
- 派发不登记看板；命中看板就绪计划任务时 `pick_ready_planner_task()` / `claim_board_task()` 复用
  `task_id`，回传后 `complete_task()` 闭环解锁下游；
- 停止信号透传，`TurnStoppedError` 终止整个请求。

### 5.2 SubContext 差异

| 维度 | `SessionContext`（leader） | `SubContext`（子智能体） |
| --- | --- | --- |
| 历史 | 跨轮会话真相源，快照恢复 | 一次性工作区，`init_chat_messages()` 仅清空 |
| 本轮输入 | `init_chat_messages()` 去末条后由 `run()` 补回 task | `run()` 追加派发 task 文本 |
| 摘要 | 有 `SummaryState` 水位、`SUMMARY.md`、后台提取 | 无水位、无摘要提取 |
| 压缩 | `compact()` 可走 Path A（有摘要）/ Path B | `compact()` 只走 Path B（无 summary_loader） |
| 快照 | turn 末落盘、可恢复 | 无快照，run 结束即消失 |
| 看板 | `get_board()` 拉取当前请求看板 | `get_board()` 返回空串 |

### 5.3 prompt 与工具

- system prompt 每 step 由 `token_budget()` 用**子智能体自身**的 `profile` 与
  `_prepare_prompt_params()` 渲染；预算按子智能体自己的 `context_max_tokens` 计算；
- 无长期记忆、无会话摘要、无看板注入；领域信息由子类自行提供；
- 工具目录由 `BaseReActAgent._resolve_tool_catalog()` 按 `tools` 白名单构建
  （`build_agent_tools()`），实现最小授权；是否可再派发由白名单是否包含 `dispatch_agent` 决定；
- `_refresh_step_params()` 只刷新 `board_desc`，子智能体无该分区。

### 5.4 结果回填与跨轮可见性

- 子智能体终答 → `ToolResult` → `ToolExecutor` 生成 `role=tool` 消息（`tool_call_id` 对应派发调用），
  追加进 lead 的 `chat_messages`；
- `add_agent_result()` 已注释停用，子智能体结果不单独写入会话历史；
- 因此**跨轮只保留 lead 的 assistant 文本**：子智能体结果在本轮以 tool 消息可见，
  下轮恢复时被 §4.4 过滤 → 追问细节需 lead 在终答中留存结论或重新派发。

### 5.5 并行与失败

- 同一 assistant 回复中多个 `dispatch_agent` 调用 = 并行：`dispatch_tool_calls()` 对
  `PARALLEL_TOOL_NAMES` 使用 `gather` + `multi_agents.max_parallel`（默认 3）信号量限流；
  其余工具串行（共享执行容器）；
- 同批参数完全相同的 tool_call 只执行一次、结果复用；
- 子智能体失败 / 空结果 → `ToolResult(success=False, message=原因)` 回填，lead 自纠（改口径重派或汇总）；
- 单个工具结果超 8000 字符由 `MAX_TOOL_RESULT_CHARS` 截断。

## 6 prompt 组装

### 6.1 流程
base_react_agent._prepare_agent方法中准备syste_prompt
每个智能体的profile各自定义，其中所需的变量由_prepare_prompt_params方法获取

PromptConfig：
`PromptConfig.resolve_fields(prompt_params)` 预渲染各字段内嵌的 `{{变量}}`，
`PromptConfig.render()` 套主模板（role/name/goal/retry_goal/constraints/resource_prompt/
expand_prompt/memory_prompt/taskbord_prompt/skill_prompt/examples/out_schema/now_time）。
预算层按字段名分区驱逐，不解析任意 prompt 文本语义。

### 6.2 step 级刷新

`BaseReActAgent._refresh_step_params()` 每 step 只重算 `board_desc`（看板随工具调用变化），
静态分区不重算；随后 `token_budget()` 重新渲染 system 并执行分区预算。

## 7 可观测

- 预算日志：每 step「总预算 / tools 前后 / system（固定+分区）/ 消息前后 / 驱逐计数 /
  compact 路径 / 截断」，以及逐分区前后与是否驱逐；
- 压缩日志：Path A/B 选择、tokens 前后、失败原因（按 `LLMErrorClass` 分类）、无效压缩回退截断；
- 摘要日志：水位推进区间、提取异常分类、失败保留旧摘要；
- trace span：`compaction/token_budget`（仅实际压缩时保留）、`compaction/session_summary`（触发即记）、
  `agent/*`；`report_context_usage()` 每 step 上报占用率与超限 streak；
- LLM 响应日志：`_trim_response_for_log()` 截断 `reasoning_content`，content/tool_calls 全量保留；
- 前端 `SessionContext.token_status()` → `calculate_warning_state()` 给出用量与预警状态。
