# 上下文工程设计

本文档描述系统**当前的**上下文工程设计。文末列出已识别但暂不实施的扩展项。

---

## 1 总体设计

设计总原则：**分层存储，真相与视图分离；逐层管控上下文规模**。

### 1.1 上下文组成

Agent 每次调用 LLM 的消息列表由四部分组成：

```
[system, *history, user(task), assistant(tool_calls), tool(result), ...]
│        │           │             │
│        │           │             └─ ReAct 工具循环消息（循环中追加）
│        │           └─ 当前任务输入（本轮用户请求 / 派发任务，永不驱逐）
│        └─ 会话历史（chat_messages 真相源注入，仅 user/assistant 文本）
└─ system prompt：固定职责约束 + expand 变量注入区
   （智能体清单 / 任务看板 / 长期记忆 memory_prompt / 历史会话摘要 session_summary）
```

### 1.2 存储分层

| 存储层         | 内容                               | 特性                                   |
| -------------- | ---------------------------------- | -------------------------------------- |
| 内存 chat_messages | 当前会话全量消息流（含 agent 回传） | turn 内真相源                          |
| turn 快照（会话目录） | 每轮结束全量落盘的消息快照        | swap-out / 会话恢复的数据源            |
| chat_message MySQL | 用户消息持久化                    | message_uid + seq，长期审计与溯源      |
| SUMMARY.md + SUMMARY_META.json | 会话摘要 + 摘要水位线        | 可从消息流重建，属于缓存视图           |

## 2 防止上下文膨胀

### 2.1 统一预算分配器（budget.py）

每次调 LLM 前执行总量管控，保证上下文不超模型窗口：

- **总预算** = agent `context_max_tokens` × `compact.contextBudgetRatio`（默认 0.85，预留输出 max_tokens 与安全余量）；
- **分区语义**（按 ReAct 消息列表形态划分）：

```
[system]          固定区：本层不动（system 内可驱逐分区由 system 重建承载）
[*history]        中段历史：最后一条 user 之前的 user/assistant 文本消息
[user(task)]      当前任务输入：永不驱逐
[assistant/tool]  ReAct 循环区：tool 消息为工具结果
```

- **驱逐优先级**：工具结果原文 → 中段历史 → 记忆注入 → 会话摘要；
- 工具结果驱逐保护最近 N 条（`compact.protect_last_n_results`，默认 5）不被降级；
- **驱逐是降级不是删除**：消息替换为占位符（列表长度不变、tool_call_id 配对完整保留），
  原文可回捞——工具结果可重新调用工具获取，历史原文在 chat_messages 快照与会话记录中；
- system 内可驱逐分区（memory_prompt / session_summary expand 变量）驱逐时重建 system_prompt，
  对应变量替换为占位文案；profile 无该变量的 agent 自动止步于消息级降级；
- **幂等与确定性**：占位符消息跳过不重复驱逐；所有可驱逐项降级完毕后止步
  （极端超限场景由后续 PTL 兜底链承担，见 §5）；
- 执行入口：`BaseReActAgent.run` 的 ReAct 循环内、每次 `think` 之前；
  预算执行结果（tokens 前后、驱逐计数）输出到日志。

### 2.2 会话历史预算（leader）

leader 注入会话历史时独立执行预算截断（`compact.leaderHistoryBudgetTokens`，默认 2500）：
超限从最旧截断、保留预算内最新消息，更早轮次由会话摘要兜底承载。

### 2.3 会话摘要（session_summary.py）

会话摘要是压缩边界的快速替换视图，服务「跨轮连续」与「历史兜底」两个用途。

**提取时机**：turn 边界后台触发（非阻塞 Task），双阈值判定：
- 上下文规模达到 6000 tokens 后开始跟踪；
- 此后 token 增长 ≥ 450，或新增工具调用 ≥ 5 次，触发一次提取。

**结构化模板**：Session Title / Current State / Task Specification / Key Files and Topics /
Errors and Corrections / Learnings / Key Results / Worklog，保证关键信息不被摘要掉。

**水位线增量提取**：
- 摘要水位存于会话目录 `SUMMARY_META.json`（`version=2` + `last_seq` = chat_message.seq，
  前 last_seq 条已纳入摘要）；seq 会话内单调递增、与消息行绑定，不随内存列表增删漂移
  （压缩重建列表、swap-out、重启均不影响）；
- 摘要输入经 ChatMessageStore.read_since 按 seq 增量读取，截到「assistant 收尾」的
  完整轮次（停止/异常留下的半轮留待下次）；单次上限
  `compact.summaryExtractMaxMessages`（默认 200 条），超限从最老未摘要消息开始截断，
  水位只推进到实际喂入的最后一条 seq，不漏中间消息；
- 旧版 index 语义 meta（无 version）或文件损坏时回退 0 全量重摘（幂等安全）。

**一致性保证**：
- 原子序：先写 SUMMARY.md 成功，再写水位 meta——meta 落后只会导致下轮重复摘要
  （幂等无害），不会漏摘要；
- 单写者：摘要后台任务是水位与摘要文件的唯一写者；
- 失败非致命：LLM 异常/空输出时旧摘要与水位均保留，等下次阈值再触发；
  摘要输出带 max_tokens 硬约束，防止摘要过长反向触发膨胀。

**卸载前保证**：会话被 swap-out 或空闲回收前强制触发一轮摘要提取（绕过增长阈值；
fire-and-forget，后台任务按 seq 水位从 chat_message 表读增量独立落盘，清理锁内不做
DB 读与 LLM 调用）。回收后内存列表消失，此机制保证摘要不缺轮次。

### 2.4 摘要与记忆的注入

leader 的 system prompt 经 expand 变量注入两路压缩视图：
- `session_summary`：当前会话摘要（SUMMARY.md 内容，空则占位文案）；
- `memory_prompt`：以当前用户请求为 query 检索的长期记忆（空则占位文案）。

## 3 会话连续

### 3.1 消息流（turn 生命周期）

```
用户请求到达
  → user 消息入库 chat_message（分配 seq）+ 内存 chat_messages 追加
  → ReAct 循环（工具调用与结果仅在本轮循环消息中，不进主对话表）
  → 终答写入 chat_messages 并入库 chat_message（表内完整轮次 = user + assistant）
  → turn 结束（finally）：
      ① 摘要提取判定与触发（后台，按 seq 水位从表读增量）
      ② 全量消息快照落盘（会话目录）
```

### 3.2 swap-out 与空闲回收

会话池后台清理任务周期执行，两类卸载动作均先保证摘要：

- **swap-out**：空闲超过 `session.swapIdleSeconds` 且无在途任务的会话，
  卸载前触发摘要保证，然后清空内存列表（快照已落盘，可随时重载）；
- **idle 回收**：空闲超过 `session.idleTimeoutSeconds` 且无在途任务的会话，
  回收前触发摘要保证，然后从池中删除；
- 执行中的会话不回收（活跃任务检查 `_is_quiescent`），避免误取消长任务；
- 已主动关闭的会话不做摘要补偿。

### 3.3 会话恢复

新请求到达已 swap-out 的会话时：

1. 从 turn 快照重载 chat_messages（全量消息流）；
2. 摘要与水位线天然生效——SUMMARY.md / SUMMARY_META.json 在会话目录持久，
   卸载前保证机制确保摘要覆盖到卸载时刻的消息列表；
3. 注入 system prompt（摘要 + 长期记忆检索）后继续对话。

## 4 可观测

- 预算执行日志：每次驱逐输出 tokens 前后对比、驱逐的 tool/历史消息计数；
- 摘要水位日志：摘要落盘时输出水位推进区间；
- LLM 响应日志：reasoning_content 超长截断，content/tool_calls 全量保留；
- 摘要提取异常：按 LLM 错误分类记因，失败非致命。

## 5 后续扩展（暂不实施）

以下能力已设计、暂不排期，作为预算分配器与摘要体系的补充演进：

| 项 | 内容 | 说明 |
| --- | --- | --- |
| recall_tool_result 工具 | 被驱逐的工具结果按句柄回捞 | 务实版：仓库即 chat_message 表、句柄 = message_uid；占位符带 msg_id，模型需要细节时按句柄回捞原文 |
| PTL 兜底链 | 调 LLM 报 prompt too long 的最后防线 | 减半待压缩范围重试（最多 N 次）→ 失败降级保头保尾截断（system + 最初任务 + 最近 N 轮，中段占位）→ 标记 degraded 冷却 → 从日志重建；承接预算分配器降级到底仍超的极端场景 |
| 环境指纹 + 时效提示 | 会话恢复校验世界状态 | cwd / git commit / 关键文件 hash / 最后交互时间；隔天重开注入「距上次交互 N 天，以下文件已变更」提示，避免基于过期状态续聊 |
| Offload 独立仓库 | 工具结果原文的独立内容寻址存储 | hash 键 + TTL/LRU 淘汰；recall_tool_result 回捞命中率不足时再启用 |
