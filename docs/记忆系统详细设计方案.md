## 1.2 与新设计的差距对照

| 维度 | 现状 | 目标 |

| 一致性 | 无 | 先文件后向量双写 + checkpoint 定时对账 |

# 二、总体架构

## 2.1 三存储职责

```
┌─────────────────────────────────────────────────────────────┐
│                      记忆系统（memory/）                       │
│                                                             │
│  Hot 核心记忆          Warm 主题记忆                          │
│  硬约束/全局规则        偏好/纠正/项目背景/资源路径              │
│  常驻每次注入           按查询语义召回                          │
│       │                    │                                │
│       ▼                    ▼                                 │
│  hot.json（唯一）     warm_*.jsonl（20M 滚动）   ← 真相源      │
│       │                    │                                │
│       │ 无向量             ▼                                 │
│       │              Qdrant warm_memories     ← 检索加速层    │
│       │                    │                                │
│       └────────┬───────────┘                                 │
│                ▼                                             │
│  MySQL 元数据（任务队列/水位/同步检查点）       ← 调度与对账    │
└─────────────────────────────────────────────────────────────┘
```

- **json 文件 = 真相源**：写入以文件为准；人工可读、可编辑、可审计。
- **Qdrant = 检索加速层**：只存向量 + 过滤字段 + 状态标签；检索以向量库为准。
- **MySQL = 系统元数据**：不存记忆内容本体，只存离线任务、消费水位、同步检查点。建表 SQL 见 `init/memory_schema.sql`（3.3 节引用）。

## 2.2 数据流

- **检索流（在线，每轮）**：用户 query → hot.json 直接加载 → warm 向量+关键词混合召回 → 三因子重排 → token 窗口截断 → 注入 `assembler.memory_prompt`。
- **写入流（离线，每 10 轮触发）**：on_turn_end 判定轮次 → 入队 memory_task → 后台任务从水位增量读对话 → 小模型提取候选 → 按主题召回判重/矛盾 → 先写 json 后写 Qdrant → 推进水位与 checkpoint。
- **生命周期流（离线，每日）**：衰减（检索时实时计算，不落盘）→ 30 天未访问软删除（双源标状态）→ 90 天未访问归档（json 压缩进 archive，Qdrant 物理删除）。
- **对账流（离线，定时）**：从 checkpoint 之后扫描 json 条目 → 补写缺失向量 / 修正状态不一致。

# 三、数据模型设计

## 3.1 json 真相源（文件布局）

```
.data/{app_id}/memory/
├── hot.json                     # Hot 层唯一文件
├── warm_meta.json               # Warm 层元信息：滚动文件清单、主题列表、id 说明
├── warm_000001.jsonl            # Warm 层数据文件，每行一条记忆 json，20M 上限滚动
├── warm_000002.jsonl
└── archive/
    └── warm_202609.zip          # 90 天归档（按月打包），归档时从 Qdrant 物理删除
```

**记忆条目字段（warm jsonl 每行 / hot.json 内联同构）**：

| 字段 | 说明 |
|---|---|
| `id` | 全局唯一、单调递增（ULID），checkpoint 与向量 point id 复用 |
| `layer` | hot / warm |
| `topic` | 记忆主题（写入时由提取模型归类，允许新增主题） |
| `memory_type` | user_correction / user_preference / project_background / resource_path（可扩展注册） |
| `content` | 记忆文本 |
| `status` | active / invalid（软删除）/ archived |
| `source_session_id` | 来源会话 |
| `created_at` / `updated_at` | 创建/修改时间 |
| `last_accessed_at` | 最后访问时间（软删除/归档判定依据） |
| `access_count` | 访问次数 |
| `invalid_at` / `invalid_reason` | 失效时间与原因（被矛盾覆盖 / 30 天未访问） |

**hot.json**：单文件、体量严格控制（建议预算 ≤ 2K token），结构 `{"rules": [记忆条目...]}`。不进向量库，加载即全文。

**warm jsonl**：追加写；每文件 ≤ 20M 超出滚动新文件；文件内不原地修改历史行（软删除/访问时间更新机制见 6.4 性能考量）。

## 3.2 Qdrant（检索层）

| 项 | 设计 |
|---|---|
| collection | `warm_memories`（全 app 共用一个，payload 带 app_id/user_id 过滤，不为每个 app 建 collection） |
| 向量维度 | **必须与 embedding 输出维度一致**：`shared/config/config.py` 的 `qdrant_size` 与 `config.json` 的 `embedding.dimensions` 统一（建议 1024） |
| payload | id、app_id、user_id、topic(keyword)、memory_type(keyword)、status(keyword)、created_at(int)、last_accessed_at(int)、content(text index，供关键词召回与过滤) |
| 点位操作 | 写入随 json 双写；软删除只更新 status 标签；归档物理删除 |
| 旧设计清理 | 现有 short_term_memories / long_term_memories / memory_consolidation_logs 三个 collection 定义整体废弃 |

## 3.3 MySQL 元数据表

新建 **`init/memory_schema.sql`**（详细 DDL 见该文件），含三张表：

| 表 | 职责 |
|---|---|
| `memory_task` | 离线任务队列：warm_extract / consolidate / decay_archive / sync_check 四类任务的状态机（pending→running→done，失败退避 1m/5m/30m，超限 dead） |
| `memory_watermark` | 会话对话消费水位：(file_name, line_no) 定位增量起点，崩溃续提 |
| `memory_sync_checkpoint` | 双数据源同步检查点：按 (app_id, scope) 记录已同步到 Qdrant 的最大记忆 id |

> 选择 MySQL 而非沿用 SQLite 的理由：与项目主存储/监控表同一基础设施，运维统一；SQLite 现实现的建表脚本与 patients 种子属医疗残留，一并清除。

## 3.4 记忆类型权重（可扩展）

类型表以注册表方式维护（`memory/models.py`），后续 agent 自我进化需要新增类型时只改注册表与提取 prompt：

| memory_type | 重排权重 | 说明 |
|---|---|---|
| user_correction | 1.0 | 用户纠正反馈 |
| user_preference | 0.8 | 用户偏好 |
| project_background | 0.6 | 项目背景 |
| resource_path | 0.5 | 资源路径 |

# 五、对话数据源评估与接入

**结论：保留 jsonl 文件方式，不改为入库。** 评估如下：

**适配性（合适的原因）**
1. 记忆提取是离线、按会话粒度、顺序追加读的场景，jsonl append-only 与之天然匹配。
2. 会话目录（`session/{session_id}/chat_history_*.jsonl`）已承担会话恢复职责，记忆提取复用同一数据源，不引入第二份对话存储。
3. 消息格式标准（role/content/tool_calls），提取 prompt 可直接消费。

**缺口与对策（需要补的）**
1. **无全局单调 rowid**（旧 SQLite 方案的水位假设不成立）→ 水位改为 `(file_name, line_no)` 二元组，存 `memory_watermark` 表；文件按序号数值排序（注意 `_10` 与 `_2` 不能按字典序排）。
2. **缺少增量读接口** → `SessionManager` 新增只读方法：从指定水位起读取本会话完整轮次消息（只取以 assistant 收尾的完整轮次，半截轮次留待下次与后续合并提取）。不改动现有写入路径。
3. **落盘时 assistant tool_calls 参数被置 null**（`append_chat_history_message` 的简化逻辑）→ 对记忆提取影响小（提取以 user/assistant 文本为主），接受现状，此处记录该限制。
4. **轮次计数**：10 轮触发的判定用监控管线已维护的 turn_number（on_turn_end 时可从 session 状态取得），不依赖文件。

**为什么不入库**：收益低（提取任务低频、延迟不敏感）、成本高（大文本字段、写入路径改造、双写一致性）；监控 MySQL 表只有指标无消息文本，无法替代。

# 六、关键机制设计

## 6.1 写入（条件触发 + 双写）

1. **触发**：on_turn_end 时轮次数为 10 的倍数 → `enqueue(warm_extract, session_id, dedup=True)`（同会话同类型 pending/running 存在则跳过）。
2. **提取**：后台任务从水位增量读完整轮次 → 小模型（独立离线模型 + 信号量限并发 + 在线让位）按提取 prompt 输出候选记忆（含主题、类型、内容）；只允许确定性长效信息，闲聊/猜测/瞬时内容由 prompt 禁止。
3. **判重/矛盾**（writer）：按主题在 Qdrant 召回现有 active 记忆 → 相似度 > 高阈值（建议 0.92）直接判重跳过；落在中间带（0.75–0.92）交大模型裁决重复/矛盾/无关；矛盾则旧条目 status=invalid（记录 invalid_at 与原因）+ 写入新条目。
4. **双写**：先追加 warm jsonl，后 upsert Qdrant；Qdrant 失败不回滚 json，留给 sync_check 补偿。
5. **checkpoint**：双写完成后更新 `memory_sync_checkpoint` 到本批最大 id。
6. **水位**：提取成功才推进（at-least-once，重复写由判重兜底）。

## 6.2 检索（召回 + 重排 + 窗口）

1. hot：直接加载 hot.json，token 预算内截断（超预算按方案约定截断后面的）。
2. warm 召回：Qdrant 向量 TopK（建议 50）∪ content 关键词召回 TopK，按 app_id/user_id、status=active 过滤。
3. 重排：`score = 0.7×语义相似度 + 0.2×时间衰减 + 0.1×类型权重`；时间衰减基于**创建时间**，建议半衰期公式 `0.5^(age_days/30)`。
4. 窗口：hot ≤ 2K token、warm ≤ 8K token（可配置）；warm 按分数优先、同分最新优先，严格控制总 token 防上下文溢出。
5. 冲突注入：检索结果含同主题相悖记忆时，prompt 附冲突处理说明（以最新时间为准）。
6. 访问时间更新：Qdrant 即时 set_payload；json 侧进内存缓冲延迟批量回写（见 6.4）。

## 6.3 衰减、删除、归档（每日 consolidate 任务内）

| 策略 | 判定 | 动作 |
|---|---|---|
| 时间衰减 | 检索时实时计算 | 不落盘，无后台动作 |
| 软删除 | `last_accessed_at` 距今 > 30 天 | json 标 status=invalid + invalid_at；Qdrant 同步标 status（检索自动过滤失效记忆） |
| 归档 | `last_accessed_at` 距今 > 90 天 | json 条目移入 `archive/warm_YYYYMM.zip`（按月打包）；**Qdrant 物理删除** |

软删除不物理清除原始数据，保障可回溯、可审计、可恢复；归档前先执行一次 json 侧访问时间缓冲刷盘，保证判定基准准确。

## 6.4 一致性与并发

- **实时同步**：写入路径先 json 后 Qdrant（6.1）。
- **定时兜底**：`sync_check` 从 checkpoint 起扫 json 侧新增/变更 → 补写/修正 Qdrant；同时抽样比对 status 一致性（json 为准）。文件变更监听按上游方案约定忽略（无手工编辑入口）。
- **性能考量（json 侧访问时间）**：检索高频更新 `last_accessed_at`，若每次重写 20M jsonl 代价不可接受 → 内存缓冲 + 定时（如 5 分钟）批量回写 + 生命周期任务执行前强制刷盘；进程崩溃丢失的访问时间只影响 30/90 天判定精度，可接受。
- **并发安全**：当前单实例部署，json 写入用进程内 asyncio 锁 + 临时文件原子替换；多实例预留 Redis 分布式锁（redis 客户端已就绪），锁粒度为 app 级 memory 目录。

# 八、落地顺序

> 原则：先清理死代码减少干扰 → 存储层 → 读链路 → 写链路 → 生命周期 → 收尾。每个阶段结束保持系统可运行。

### 阶段 0：清理与环境（0.5 天）
- 删除幻影工具名引用（permission / tool_executor / monitor_pipeline 的 MEMORY_TOOL_NAMES 及相关分支）。

- 维度对齐、Qdrant/Embedding/建表等第七节环境项逐项确认。

### 阶段 1：会话摘要解耦 + json 存储层（1 天）

- **验收**：hot 记忆注入生效；手工构造 warm jsonl + 手工向量化后可通过 vector_store 检索到。

### 阶段 2：检索链路（1 天）
- 新增 `retriever.py`（混合召回 + 三因子重排 + 窗口控制 + 访问时间更新）；重写 `memory_manager.py` 门面。

### 阶段 3：写入链路（1.5 天）

### 阶段 4：生命周期与一致性（1 天）

# 九、风险与开放问题

| # | 风险/问题 | 应对                                                |
|---|---|---------------------------------------------------|
| 1 | 大模型提取质量不稳定（写入噪声） | 提取 prompt 严格白名单式写入要求；判重高阈值宁漏勿滥；consolidate 每日二次整理 |

| 5 | 旧 md 记忆是否迁移 | 不迁移                                               |
| 6 | embedding 限流 | 批量接口 + 失败重试；提取任务本身低频（10 轮一次）                      |
